# Bourse · Save and sync

Owner-requested design for the shared save, for insertion into the public plan. Authored with Codex, OpenAI GPT-6 family. The exact runtime model is gpt-6.2-sol.
The design and all source line references use commit `5960ebfa8e686760db85c890b619537e3081cd81`. This is original design work. Implementation and release verification are future work.

## 1. How a device knows what happened

A device saves an edit with the identity of the edition it edited. Removing a record leaves an instruction naming that record.
A phone returning after months can therefore distinguish a new item from an old copy of an item the player removed.
Two devices can buy the same quantity. Each purchase has its own receipt. The stock figure includes each active receipt once.
When two edits disagree, the app can keep both complete editions and show what each would do. Closing the question leaves each player's screen on its last valid edition.
A backup from before these records existed cannot explain a missing entry. The player sees both sides before anything moves.
The same rules cover Tracker ticks, Lists stock and the other modules. There is no second set of decisions for a sync that started in Settings.

## 2. Decisions

**S1. Save editions and edits.** [Rejected: inferring intent from two finished snapshots or from the time of the last write.]
Keep the existing shared fields as a readable picture of one accepted edition. Alongside them store a portable history of small transactions.
An edition names its parent editions and records only the logical values that transaction wrote. Its identifier is a digest of its complete contents.
The history is a directed acyclic graph. A parent is what the writer had actually applied. Merely downloading an edition does not make it a parent.
A transaction that removes a value writes a tombstone, an explicit `del` at its logical path. An untouched or unrepresented field emits no operation.
Empty container frames are structural. An absent map entry, an explicitly stored zero, an omitted legacy section and a tombstone have separate meanings.
Ordinary edits have one parent. A new source starts with a checked snapshot and a declaration of its scope. Only a completed reconciliation may have several parents.
Store a given edition once. Unchanged syncs add no editions. Keep tombstones, receipt identities and the ancestry they need for the life of the history. S13 defines space recovery.

**S2. Merge the evidence before changing the displayed save.** [Rejected: a local-side default, a 200-upload lookback, and interpreting a missing base as an empty save.]
Union the validated editions by identity. A tip is an edition with no known child. To merge related tips, for each logical path gather their last writes.
Discard a write only if another write to that *same path* descends from it. Share the result when all surviving writes agree, including two explicit removals.
A single surviving addition is new to a branch that has never written this path in the same history. Two different live values, or a removal concurrent with an edit, require a decision.
For a common base, this gives the usual one-sided edit and unchanged-side outcomes, including a write that deliberately returns a field to an earlier value.
For example, both devices start with a watch target at 500. The phone removes that edition while the computer changes it to 450. Both writes name the 500 edition. Neither supersedes the other, so the player sees both choices. A watch added on a separate path remains a distinct addition.
Without a cached base, the same computation works from the portable parents. An unresolved parent, invalid digest or cycle is damage, never proof of absence.
If roots are unrelated, a load explicitly broke the link, or a known cloud file was replaced, use each applicable materialized edition and its declared scope. If more than two tips are involved, retain and show every distinct competing value with its source edition.
Equal values need no decision. For *every* unequal in-scope unit, including one-sided values and stock evidence, show what each side holds and where each result would go.
A source that never represented a module has no say about it. For detached comparison, a partial source never asserts absence outside its declared scope. When a bridge retains an out-of-scope section, carry its current checked fields and dependencies as part of the reviewed result. A truly new device gets “Take the cloud save” or “Later”. Its empty setup cannot remove cloud records.
For this shortcut check all modules and Tracker details, settings, exclusions, values, history and pending work. A used save with zero characters can still have a full Atelier or Lists section.
For first-time links between used copies, group by module and allow expansion and per-entry decisions. Whole-list, fleet and stock constraints apply to either input order.

**S3. Keep the last valid edition on each device until the decision commits.** [Rejected: storing a provisional count, per-key undecided lists, or a partial merge base.]
Each device has one active edition and a set of competing tips. The cloud also has an active edition and tips. Each active edition must reconstruct to a valid save.
Publish outstanding editions as proposals by a conditional write, leaving the cloud's active edition intact. Store the union and the local active pointer atomically before opening a question.
Closing it changes no active pointer. Proposals carry complete reconstructible alternatives through reload, file, code and OneDrive. Until publication is confirmed, say “Saved on this device only”.
After verified publication say “Both copies are backed up. Choose how to combine them.” A third device adds its branch even if it never saw the earlier question.
Ordinary work on unaffected items may continue on its device's active edition and be backed up as another tip. Applying the combined picture waits for all required answers in that sync.
Disable an action whose inputs or outputs touch a disputed stock group, including a craft's ingredients, outputs, step changes and Undo. Explain which item blocks it. A rejected action writes nothing.
Bind an answer to the exact sorted tips, both displayed active identifiers, the shown values and dependent rows, local revision/epoch, account, cloud item and provider tag.
Re-read at commit. A new tip or changed dependency requires a fresh preview. A resolution writes the chosen values or tombstones, even for a value numerically unchanged, over every rejected alternative.
Two independent answers with different edits remain two branches. A later answer can supersede only versions it saw. No purchase needs a new name to reverse an earlier decision.
A “keep for now” or dismissed dialog has no effect on subsequent comparisons. Settings shows “Answer now” on unattended sync. Sign-in and manual sync can open the question. Tracker waits until visible.

**S4. Authorize loss in both directions.** [Rejected: counting only ticks lost from the device that asked.]
Before changing an active edition, compare the proposal with *each* active input. List any live row, count reduction, character, child or purchase that would disappear or be displaced.
Show “Remove from all devices” with the item(s), quantities and consequences, “Keep”, and “Later” for a contested removal. An explicitly approved, causally covered removal can travel.
Record its authorization against the exact previous writes, path and effect. It cannot authorize removal of an unseen edit, new child or a separate purchase.
A local-only erase or file replacement has no cross-device authority. Retain the Tracker's incoming-tick confirmation on each receiving device. Cancellation keeps its own edition and the proposals.
For a directly initiated edit, consent binds the editions and exact rows being changed. A receipt from a foreign file can explain past actions but cannot grant permission for a new cross-device loss. A stock purchase or Undo made with explicitly stated Lists and sync effects can authorize that exact receipt and quantity. Ordinary independent credits never ask merely because their displayed totals differ.
For compatible field-wise merges retain Lists' header/children, duplicate-ID and target rules, Submersibles' company/submarine/voyage and slot rules, and the placeholder-name and discovery rules.
Apply them to typed units after collecting history. A list delete versus a new child names every affected target. A fleet choice names every affected voyage. No orphan or unshown deletion may materialize.
Each transaction records its logical writes together. Trace changed paths back to their transaction when combining branches. Re-evaluate a compound action's expected inputs and inspect all its writes when a conflict intersects it. Treat actions linked through the same stock, wanted item or fleet dependency as one selection if they cannot be independently validated. Compound business actions remain indivisible. If choices split a craft, hand-in, bulk tick or dependency group, offer whole valid alternatives or a checked recomputation with the effects shown.

**S5. Commit local intent against the stored edition.** [Rejected: saving a page's whole cached document or selecting the “newer” sync record by a clock or counter.]
A page submits its changed fields or a named command, its observed before-values, revision and epoch. Read current main, guard, revisions and device state in one IndexedDB transaction.
For a stale revision, replay disjoint intended changes on the current edition. For an overlapping change, refuse with the current value and retain the player's draft for comparison. A different epoch requires reload.
Never synthesize removals by comparing a stale whole page with the newer store. A Tracker write owns its character/Tracker intents only. A module can change other sections only through an explicit checked compound command.
Recompute all dependencies against the same stored edition. Commit its materialized fields, history, private changes, guard and revisions together. Return the committed state before reporting success.
Notifications on both page channels refresh displays. Correctness survives silent channels, a suspended page, a fast path, and an already queued debounce.
Only the sync **acknowledgement** sets a non-null cloud receipt. Loading, restoring, keeping, erasing or going back invokes a dedicated replacement operation that clears the receipt and rotates the epoch in that transaction.
A later ordinary save, stale success callback or Settings character save has no API to set that receipt. Update `fc` and `backupAt` only with a successful operation that owns the field, preserving other device fields.

**S6. Model the player's stock separately from receipts.** [Rejected: merging displayed totals, adding the same receipt twice, or clamping a joined result.]
For each Lists owner and item, keep the player's own stock in each quality and a set of immutable receipts. Normal and high-quality totals are own stock plus credits on their active receipts. Collectables have no Bourse credits.
Project all three totals to the ordinary Lists `have` entry in the same transaction. A missing quality reads as zero. An all-zero entry may be absent even with an active receipt, after stock was consumed.
Allow a negative own part. Calculate exact integers and reject a proposed materialization outside 0–999,999. Never infer a missing purchase from a count and never infer that a receipt disappeared because a list became shorter.
At every v2 seed, encode ordinary stock quantities as typed own-stock paths, even before the first Bourse credit. Both adapters address the same logical register from the start. Preserve the exact existing Lists unit/presence representation for untouched stock. On a no-credit item, apply the original whole-unit Lists policies to these paths as a group. For an ordinary Lists edit, adopt the result of its existing stock operation, subtracting current active credits to get the new own part.
For a Bourse purchase, leave own stock intact and record only the amount accepted by Lists. For Undo, cancel the specific receipt and leave own stock intact. Do not issue a second independent Lists Undo for that Bourse credit.
For uncredited stock keep existing Lists merge outcomes and expected-value guards. When either branch has credit history, handle the complete stock group before ordinary Lists remove-versus-edit logic. Lift the old untouched stock value to an own part when joining with the first credit.
Merge own stock by quality as a versioned value and receipts by distinct identity. For a known undone receipt, cancellation of the same body supersedes its old active edition. Equal purchases under different IDs are distinct.
For identical immutable bodies across detached saves, a recorded cancellation offers the reconciled cancelled state with its exact stock result. Show it whenever it would remove a live credit. A live-again state needs an explicit decision that saw that cancellation. Absence without any state is unknown. A missing receipt with no explained transition, competing own amounts, conflicting receipt states, a negative joined total or overflow requires a preview of all valid branch groups. Each includes every receipt and all three counts.
Offer the valid existing groups and, when possible, an explicit combination of receipts and an entered valid stock figure. Show personal contribution, total, and every activation/cancellation. A decision rewrites all disputed memberships and own parts together.
An invalid candidate is never an option. Re-accepting an explicitly cancelled receipt requires a new decision over that cancellation. Record a cancellation with the original body for every rejected receipt, even when the chosen edition did not contain its ID. A receipt's logical path accepts only an immutable body with a state, including for an uncredited tick. Hide cancelled marks from active rows. Two bodies claiming one immutable receipt ID are damage and cannot be selected as an arithmetic result.

**S7. Bind a tick to what the player bought.** [Rejected: inferring a purchase from a change in demand or crediting each selected list for the entire row.]
Default to “Tick only”. With “Also add to I have in Lists”, allocate the purchased amount across the displayed owners using the plan's stable share order. Verify the selected lists, quantities, per-owner source targets, trip and existing marks inside the write.
Record each owner's actual purchase and actual credit. Own trip items always credit zero. At the cap, show the purchased and accepted quantities separately. From 999,990 a purchase of 40 records 40 bought, 9 credited, and 31 uncredited. If any Lists part refuses, commit none and offer a separate tick-only action.
For a combined row allocate in the order `c1…c8,u,x`, each limited to its outstanding need. Quantities beyond the outstanding need require the player to edit the purchase before recording it. Generate the purchase IDs once before dispatch. Retry only that command in its original page for at most two minutes and three attempts. Read the receipt, tombstone or local completion record before retrying. An unknown result after expiry requires a fresh view.
A purchase stays bound to the exact wanted items and amounts behind the displayed need. Subtract the uncredited part once. A different source, unexpected need, or incompatible check mark displays “To check” and excludes the row from a spending total.
For an own item, the remaining quantity is its trip quantity less the sum of active purchases, floored at zero. For a Lists row, consider only this trip, owner, item and quality. Use the causally latest active purchase/check anchors. All simultaneous latest anchors must agree on the source fingerprint and expected need after their own credit (`of − cr`). If that equals the actual current need, subtract the sum of active uncredited units (`n − cr`) once, with a floor of zero. Otherwise keep the marks and show “To check”. No display count participates in a stock write.
“Still count” writes a check against the current sources. Removing an uncredited mark requires confirmation. Undo of a credited purchase verifies the whole action and current stock, subtracts the recorded credit only if enough remains, and records the cancellation.
Allocate a trip on the first add, tick or shopping-list copy in the same write. “New trip” creates a fresh ID, clears only this trip's own items and uncredited marks after confirmation, and keeps previous credits and their Undo available.
Two offline starts get different IDs. Ask which trip to display. Keep the other trip and its own quantities accessible. A change of selection or current trip never cancels a receipt.
Hide the credit switch automatically when its build tests fail. Retain the reader and indivisible stock-group guard in the off build. With existing credit history, display/export it and refuse stock-changing actions or divergent merges for that group with an explanation.
Tick-only still works for unblocked rows. Never apply a cached `lists` preference as a grant of credit in the off build. A credit-enabled build can finish a held decision.

**S8. Use a separate cloud file and conditional writes.** [Rejected: blind path replacement, a best-effort create followed by a read, or a tag unrelated to the downloaded bytes.]
The legacy file is `eveniunt-command-center.json`. The v2 save uses `eveniunt-command-center-v2.json` in the app folder. The updated app has no writer for the old path, including its v1 fallback.
Fetch metadata and content for the same authenticated drive and item. Use a version-specific read, or bracket the body read by metadata reads with the same item ID and exact opaque `eTag`. Reject mismatches, missing tags and incomplete bodies.
A missing item is distinct from invalid JSON, an unsupported future version, access refusal and a failed download. A future version gets a reload notice. Only a proven name lookup miss can enter creation.
Reject a renamed or moved item, or a name now bound to a different item. The version-rising build must verify the provider also invalidates the item precondition on a rename/move that could redirect a pending replacement. Use a provider route documented to fail if the name exists *at final creation*. A candidate is a Graph upload session naming the item with conflict behavior `fail`. The build must prove the chosen route and its exact final request.
Keep create disabled until the documentation and ten refused creates against an existing file on personal OneDrive, with byte comparisons, are recorded. Test simultaneous finalization and disabled behavior. The version-rising release waits for that evidence.
Replace by item ID with the exact strong provider precondition (`If-Match` with the observed tag). Never retry by path or with a missing or wildcard tag. Conflict, missing item or changed account starts a fresh read and preview.
After every write require the expected item ID, the new tag and a stable read-back of the exact expected envelope identity/content. An ambiguous reply advances nothing. Rediscover by name and verify the intended item before accepting a later observation.
After a create collision, inspect and merge the winner. When the file vanished, create only under the verified condition. Preserve local proposals and start a fresh file generation. The old cloud file is never a repair source.
The file generation changes on create and damaged-copy overwrite. A generation or item change breaks the local link regardless of counters. Within a generation use actual parent containment, never an upload count, to establish ancestry.

**S9. Serialize the single legacy read, including during a first-device race.** [Rejected: letting several prospective creators fetch the old file, or letting a missing v2 file renew permission.]
A cleared browser cannot distinguish a first install from a deleted v2 file. Keep one durable spent bit per authenticated personal drive and fixed migration number, outside the save file. Normal sync of an existing v2 file never consults or depends on this bit.
On a genuine name miss, with creation verified, generate an invocation nonce and proposed file generation. **Before any initial v2 file can be created**, the sign-in helper atomically inserts the spent row if absent. Bind it to this invocation and generation. Derive drive identity from the authenticated session. Sign-out, reinstall and file deletion cannot reset it.
Only the first successful insert returns a grant, held in that invocation's memory. A duplicate or lost response never reissues it. If spent status is unknown, do not start a new file in a grant-eligible migration. Known spent or permanently disabled status permits create-only recovery from player data, without a legacy read.
Reserve the new filename through S8 with a recoverable initializing envelope (`seed=pending`) holding the creator's guarded edition. A non-grantee first rereads for the winner. If still missing, it may create only a device-data recovery copy. A race can forfeit the automatic read, never duplicate it.
Only the invocation holding the original grant **and** a confirmed successful create/read-back of its matching pending generation may initiate the old content request. Consume the in-memory grant before dispatch. A restarted creator, a create loser, later mover, overwrite or recreated file is ineligible. There is no old GET before election or during ordinary sync.
Make one logical, non-retried content request including its provider redirect. Cache returned bytes in durable guarded staging before parsing. An uncertain grant or a crash before durable staging can forfeit the automatic transfer. Use the player's own saves and the local-file recovery below. A damaged legacy source stays available as raw input.
Bootstrap failure cannot block ordinary use of a valid v2 file. Keep `seed=pending` while ordinary updates add proposals. Mark it `imported` only after the staged legacy bytes are durably represented, `none` only after a confirmed legacy miss, or `manual` after acknowledged file recovery/continuation. Other writers preserve this field on every conditional update. A late result from the initial invocation cannot overwrite a newer active edition or reverse a finalized seed state. Show “Older cloud data has not been brought in” until the outcome is known or the player acknowledges continuing from available saves.
A healthy, initialized, strongly consistent helper store is required for issuing grants. If its continuity cannot be established (including restore from an old service backup), disable grant issuance for that migration, retain v2 sync and offer file recovery. The helper never receives save contents.
For the winning legacy read, compare the old snapshot with the local v1 snapshot inside its declared scope. A real legacy base from that *same old item and account*, when provenance is established, can be shown as a difference aid. Absent proof, use S2's detached comparison.
The historical receipt has no tag or authenticated account binding. Never reinterpret it as v2 ancestry. Use explicit player confirmation for one-sided legacy data, even if a comparison aid suggests a removal. A first legacy Tracker-only copy leaves other modules alone.
Join the staged result against the *current* v2 item under S8. Another device may already have changed it. Every later device brings only its own local save and uses S2 on first link. A later device with typed stock 12 can retain that own part plus a separate 40-credit receipt, with the preview showing 52.
For a cleared older device, Settings offers “Bring in a saved copy”. Explain how to download the older file from the player's own OneDrive app folder or export from an older device, then select it locally.
Decode the original compressed legacy cloud envelope as well as old backups. Preview the selected records alongside v2 and save accepted choices with S2–S6. This action sends no request for the legacy path and never changes that file.
If all copies of those late edits have been lost, identify them as unrecoverable. Until its update or a player-supplied recovery, the older device's later work stays on the older side.

**S10. Separate local durability from a cloud acknowledgement.** [Rejected: a mutable sync base in page memory and updating it before the merged data lands.]
At sync start flush the initiating page's intended edits, read the guarded store, then capture its epoch, revision, active edition, tips, drive binding and a fresh attempt ID. Settings uses the full stored document even with zero characters.
Before making a request that can change OneDrive, durably record the expected item/tag (or create-only name), candidate identity and attempt. Allocate the new revision before committing the preparation. Store that post-preparation revision in the attempt and return it to the caller. A preview drawn after a staging write binds to the post-staging revision as well. Re-read guard and tokens immediately before dispatch. Serialize this last check and dispatch with local replacement.
One implementation is a short transaction covering the main store. Within it, compare tokens and synchronously initiate the prepared fetch within the final read callback. Stage and hash the body before that callback. Never hold an IndexedDB transaction awaiting network I/O.
On response, recheck the account, attempt, epoch and guard in a fresh write. Install exactly the acknowledged save/receipt together. If only ordinary edits intervened, retain their branch and reconcile from the actual stored edition. The receipt points to exactly the cloud active and tips last witnessed. It never claims that an unadopted cloud edition has been applied locally. Never run a silent default-choice second merge.
A changed epoch or recovery state discards the callback. An in-flight HTTP request may already have arrived. Show an unconfirmed attempt until a fresh stable read establishes its outcome. Its item/tag condition protects intervening cloud writes. Local Restore always works offline.
A lost response, quota failure after upload, partial identity or superseded attempt cannot mark the device synced. On restart read the cloud again before sending. Identical verified content needs no upload. Keep a confirmed backup time separate from a completed reconciliation.
For damaged bytes, first offer download, then ask explicitly to replace the displayed copy with this device's checked edition. Bind consent to exact old bytes/identity, local revision, account and epoch. Refuse unsupported future formats, absent tags and unstable reads.
If another device repaired it, read and merge that sound copy. An exact return of older valid cloud bytes can have the same item and generation. Compare the fresh graph with the last confirmed active edition **and every then-confirmed tip**. Missing prior history breaks the link, even if a counter or one common ancestor matches. An exact body match or proved containment allows normal comparison. A confirmed overwrite starts a new generation with no authority from the damaged file. Retain validated pending local editions. Other devices must compare afresh.

**S11. Release the erase fix first and keep a local guard.** [Rejected: relying on a cache expiry date, or writing the safety copy in a later request.]
At the real post-module-moves baseline freeze the built files as `old0`. Release only the Tracker erase fix and rebuilt bundles as `old`. Record when the fixed website actually went live.
In that fix validate inside the erase transaction. On unreadable/newer data refuse with the reason, offer rescue and keep the screen open. On readable v1 or genuine first use preserve the existing Tracker-only meaning. Never clear page state until commit.
At least 30 full days must elapse from live publication before the version rises. Recheck every writer on the real baseline. A second old destructive writer needs a remedy, tests and the corresponding protection interval before the rise.
Before the first guarded write persist and verify the storage-home marker. Atomically write main, its revision, a complete independent guard and its matching revision in the same IndexedDB store. Include device state needed to recover proposals.
Check both copies on every read and just before every write. A valid guard with missing, unreadable, lower-version or mismatched main enters recovery. A v2 main with missing/broken guard is also a recovery case. Never silently bless it or create a blank save.
Show both dates, sizes and exportable originals. Restore copies valid guard contents. Keep requires a separately checked, readable main and a second confirmation. Archive displaced raw bytes before installing the selected content. Missing/malformed content cannot be chosen as the new save.
Compare *both raw identities and revisions* inside the action. Missing-revision and missing-data states are distinct. Stale dialog, new generation, unreadable future version or quota failure leaves storage untouched. Redisplay current state. Two invalid copies permit raw export and explicit recovery from a valid supplied backup.
While recovery is pending, no ordinary write, legacy read, upload, cleanup or sync finalizer runs. A replacement rotates the epoch and drops the cloud link even if its user data happens to be equal.
Show “Reload the page to update” in updated refusal paths. Ship the instruction to reload **every** open page online. Frozen binaries keep their observed messages. A cached Atelier can appear usable while saving nothing to the shared store.
A guard recovers the last guarded save. Clearing the entire origin can remove both copies. A separate backup or a verified cloud copy is then the recovery source.

**S12. Choose storage once and import by the source's scope.** [Rejected: per-call fallback after migration, trusting a file's device fields, or changing the screen before the save succeeds.]
Once IndexedDB is the recorded home, a transient open failure cannot select localStorage or memory as a new home. Check for an existing v2 main or guard on any accessible authoritative store before migration.
To move a real v1 fallback save, re-read its bytes under cross-tab exclusion, copy and verify them into IndexedDB, and keep the source. If two readable stores differ, offer both. Uncertainty about the authoritative home stops mutation and offers export.
If the guard cannot fit, retain a genuine v1 store. Updated v1-mode pages can edit supported legacy fields and use v1 backups/codes. They cannot save Bourse data, adopt a v2 file or sync to either cloud file. State “Local older-format save only. Updated devices do not exchange changes here.” Supply export and retry.
Before each v1 mutation re-read the actual stored format and check the proposed save for v2-only data. Serialize fallback edits among updated pages with a same-origin lock and recheck expected bytes. Without safe exclusion, offer read/export and explain the failed write.
Never claim such a lock protects against an actual old binary using localStorage. Retain divergent source bytes through migration and offer manual recovery. Memory mode displays “not saved”. True older binaries can still sync the old file independently.
Use quota recovery once per action. Keep at most 60,000 price-cache records, evict only prices, close connections and allow five seconds for confirmed clearing before one retry against fresh input. Keep attempt times, request gates, save and guard. Show storage use and a manual clear action.
For any backup/code, decode, validate, show scope and losses, then archive and atomically adopt the selected data locally. Native files carry histories and pending tips. Ignore device fields, sync bases, credentials, home markers and merge authorizations from untrusted external files as grants of local authority.
If Lists is supplied, its counts and the corresponding credit evidence come from that source together. For v1 Lists with no Bourse, imported totals become own stock without imported credits. If Lists is omitted, preserve the local stock group, including its receipts and cancellations.
A Bourse-only file cannot install credit-bearing data independently. Keep its raw group available for explicit reconciliation. Preserve independent supplied Bourse fields, and keep omitted modules. Rebuild a validated, scoped replacement edition. An incomplete splice never borrows the source's ancestry.
In all cases rotate epoch, discard the cloud receipt and require a detached comparison at the next sync. Loaded bytes never fabricate proof of a deletion. A local restore to 250 ticks cannot auto-remove 50 from a cloud copy holding 300.
Desktop “Add” and “Replace” name the selected characters and the Tracker fields the importer owns. Compute alias, link and rename effects on a working copy. Preview any removals, then commit one checked intent. Other modules, receipts and stock come from storage.
“Go back” archives the current save, replaces only the old Tracker scope, preserves other modules and their history, and detaches. A pre-shared-save catch-up may still contribute Tracker changes, with omitted modules marked unrepresented.
The shopping-list copy requires the matching hosted origin, validated device entry and item mapping. Preserve source bytes, sum duplicates, count unmapped entries, use normal quality and the larger of imported and live quantity, capped at 99,999. Commit its trip, rows and device receipt together only after at least one valid row survives.
A missing source, foreign file origin, storage refusal or all-invalid input leaves the attempt available. Display copied, skipped and capped counts. Older edits made to the source after a completed copy need explicit user import.

**S13. Bound history without forgetting old deletions.** [Rejected: expiring tombstones by date, device count or upload count.]
Ordinary sync sends a compressed dictionary of editions with one copy of each transaction. An idle sync adds no history. Dominated tips drop from the tip list. Their transaction evidence stays reachable.
If the body exceeds the cloud ceiling, stop before sending and offer a full portable backup. Show actual bytes. A deliberate “Start smaller history” is available only from a single resolved, complete edition.
Export and verify a complete re-readable archive first, then show the effect on returning devices. On explicit confirmation create a fresh genesis with all current values, intact stock evidence, active receipts and their IDs. Retain cancelled receipt identities and their immutable bodies for idempotent Undo comparisons.
Install it under a fresh cloud generation by S8, keeping a local archive until confirmed. If this cannot shrink enough, stay on local saves and file transfer. A detached old device compares its entire claimed scope. Omission after compaction cannot resurrect or remove a row automatically.
No automatic pruning of unresolved tips, raw recovery bytes, deletion evidence in a live history or undelivered local work. A downloaded archive contains history, including earlier contents the player once removed. Say so on export.

## 3. Data shapes and validation

**Portable records.** All new names below are wire names. Dates are informational Unix milliseconds, finite nonnegative safe integers. Sequence, expiry and conflict ordering never depend on device wall time.
A validated local replacement always creates a distinct seed, even for a byte-identical old snapshot. For a native file, copy its original checked nodes and active/tips as a read-only source bundle under the seed's `source` reference, deduplicated by ID. Preserve the source's pending tips as outstanding alternatives. That reference proves provenance only and cannot cause a causal fast-forward. A rolled-back active edition thus remains an actual proposal even when its original node is an ancestor of the cloud tip. A device that vanishes after staging the restore cannot erase the question.
The v2 shared document has `{app:"eveniunt-command-center",v:2,updated,chars,modules,device,moved,history}`. The public portable part is `{chars,modules,history}`. Device bookkeeping and local archives never cross that boundary.
The active snapshot remains directly readable in `chars/modules`. It must match replay of `history.active`, including the projection of every stock group. On mismatch preserve the original and stop before arithmetic or upload.
Both legacy tags stay readable. A new backup is `{app:"eveniunt-command-center",kind:"backup",v:2,saved,save}`, with the existing ISO date field. The new transfer prefix is `EVT3-`. Read `EVT1-`, `EVT2-`, v1 native backups and Tracker-only `eveniunt-completionist-tracker` backups with their original scopes.
Cloud outer `{app:"eveniunt-completionist-tracker",v:3,format:"deflate-raw+base64",data}` wraps a checked inner `{app:"eveniunt-command-center",v:2,generation,seed,chars,modules,history}`. `generation` is fresh random 128-bit hex. `seed` is `pending|imported|none|manual` (`manual` means device/file recovery). It never grants a read.

| Field | Accepted representation and rule |
| --- | --- |
| `history` | `{v:1,active,tips,nodes}`. IDs are 64 lowercase hexadecimal SHA-256 digits. `tips` is a sorted unique array of the maximal nodes in the retained graph, nonempty. `active` can be their ancestor and is separately retained. Require every referenced node and all its parents. Optional seed `source={active,tips}` refers to a fully checked, closed source subgraph in the same dictionary. Retain those nodes for replay and backup. Source references are distinct from parent edges. Compute top-level tips over the working graph only, with unresolved source tips explicitly enrolled as alternatives and the old source active carried by the new seed's picture. Reject reference cycles of either kind. |
| `nodes[id]` | `{kind,parents,scope,nonce,ops,consent,source?}`. `kind = seed/edit/merge`. Parents sorted unique IDs, zero for seed, one for edit, one or more for a merge/explicit confirmation. Each list is bounded by the validated enclosing byte ceiling. A fresh seed uses a random 128-bit hex nonce. Normal edits use a unique 128-bit hex command nonce. Fully automatic merges use a fixed null nonce. |
| Identity and replay | Hash the UTF-8 RFC 8785 canonical JSON of the complete node, excluding the dictionary key. Require well-formed Unicode, exact finite numbers, unique keys, acyclic closed graph and equal bytes at equal IDs. Traverse iteratively, memoize ancestors/last writes per actually changed path. A differing body with the same ID stops the merge. |
| `scope` | A seed uses `"all"` for a complete native save, or `{chars:boolean,modules:[names]}` with sorted unique module names for partial legacy input. An omitted module is unknown there. Other nodes inherit the union of represented scopes. Their `scope` field is that exact resulting declaration. A detached replacement of a composed local save starts a complete seed. |
| `ops` | Sorted unique entries `{p,op:"put",value}` or `{p,op:"del"}`. `p` is a typed path encoded as an array of components, never a concatenated property. Seeds enumerate present logical values. Empty arrays/maps intrinsic to a value remain literal. Initialized empty schema frames are reconstructed by the adapter. |
| Logical paths | Tracker paths distinguish character existence, its name and other profile fields, tick, exclusion, level, availability and setting. Module paths carry module, group and unit using existing per-module boundaries. Stock-own path `["own",owner,item,quality]` and receipt path `["receipt",id]` precede generic Lists/Bourse flattening. A section with unrecognized semantics is one opaque lossless value. |
| Path/operation checks | Reject unsafe segments, duplicate paths, prefix overlaps, unknown operation/version or wrong scope. Use the existing module and unit alphabets (`save.js:22–26,150–152` and `model.js:63`). New reserved paths use only the listed components. Canonicalize safe external data without slicing it. A seed or node that would silently normalize existing player data is held for raw recovery. |
| `consent` | Sorted entries `{p,before,effect}`. `before` lists the exact maximal write IDs for that path that were shown, including competing inputs. `effect` is the digest of the chosen operation and its sorted dependent path/value changes. Missing consent is the empty list. Consent is tied to the shared history and valid only for the covered inputs. |
| Merge evaluation | A valid merge node must resolve every unequal maximal write or pass a specified module rule, satisfy all dependencies, and materialize to one valid edition. An inherited parent does not overwrite another parent's value by order. For a reviewed detached bridge, explicitly write every decided difference, including the known side's absence as a tombstone. Record origins as parents only after this review. |
| `modules.bourse` | `{v:1,watch,extra,bought,own,prefs}`. All groups are maps, empty frame allowed. `bought` is the active edition's receipt table, including cancelled receipts. `own` stores the group's personal stock where credit history exists. They mirror the typed logical paths. A single authoritative operation feeds both projections. All v2 seeds encode personal stock at the same logical paths. Uncredited stock can use its existing Lists encoding on the visible document until its first credit. Preserve explicit zero-field or absent-field layout on untouched legacy units. |
| Watch and own trip items | `watch[item.quality]={target,at}`, target 1–999,999,999. `extra[trip.item.quality]={qty,at,t}`, qty 1–99,999. Trip ID equals `t`. Item is a canonical positive decimal up to eight digits, quality `nq/hq`. For pre-release two-part keys, use the recorded trip or `legacy00` and the larger amount on duplicate. On the first real trip adopt legacy items in the same transaction. Record mismatched redundant trip IDs for recovery. |
| Purchase identity and body | New trip and receipt IDs use 16 cryptographically random lowercase base-36 characters, checked unused locally. Accept existing 8–16 such characters. `bought[id]={body,state}`; `state=active/cancelled`. Immutable `body={o,i,q,n,of,cr,ls,t,at}`: owner `c1..c8/u/x`, item/quality as above, `n,of` 0–999,999, `cr` 0–`n`. `x` always has zero credit. A check record has `n=cr=0`. |
| Need evidence | New `ls` is the full SHA-256 digest of sorted (selected list, target key, per-owner requested quantity) tuples. Recompute against canonical source values before applying even when quantities match. Retain older 12-character fingerprints or absent `ls/t` losslessly and mark the row “To check”. Resolution binds also to the displayed receipt set. Never use `at` to settle competing checks. |
| Personal stock | `own[owner.item]={nq,hq,coll}` stores signed safe integers internally. `coll` remains 0–999,999 since it has no credits. Sum credits with exact integer arithmetic before range checking. A present native credit or cancellation requires a represented group. A native cached total inconsistent with its group is damage. A missing displayed count is valid when its derivation is zero. |
| `prefs` | `area` maps the seven supported data-center names to 1, `lists` maps existing-format list IDs to 1, `trip` is a trip ID. `home/taxCity` are known world/city names up to 40 characters. Retain unrecognized old names as unselected values. `oldDays` 1–30, `dropDays` 1–90, `within` 0–100, `alertMin` 15–240. `split=fewest/cheapest/within`, `route=savings/items`, `tick=only/lists`, `rankBy=sales/listing`. `alerts/gatherFree` are booleans. Omitted defaults follow the public plan §§2, 6–8. |
| Local storage | Dedicated `main,main-rev,main-guard,main-guard-rev`. Epoch/revision/attempt IDs are random 128-bit hex tokens in new writes. Legacy revisions are opaque strings. `device.epoch` is minted on migration and every replacement. A storage-home marker records `indexeddb` before migration. Archives retain raw bytes and their source, keyed with a fresh ID. |
| Device receipts | `device.bourse={mcopy?,done?}`; `mcopy={at,copied,skipped,capped}`, with nonnegative safe counts. The command receipt is `done[commandNonce]=at`, retained at least 24 hours and through every live retry. `device.tracker.sync` retains `fc,backupAt` and a nullable `drive={account,item,tag,generation,bodyHash,active,tips,at}`. `at` is ISO UTC. Imported legacy receipts are read as legacy only. No ordering or authority is derived from `at`. |
| Local transport | `device.transport={detached,attempt?,legacyStage?}`. `detached` survives a crash until the reviewed link commits. `attempt={id,epoch,rev,account,item,tag,bodyHash}`. Item and tag are null only on create. Store original prepared bytes or a reference to immutable locally staged bytes. `legacyStage` identifies the preserved single response by its digest, with status. Opaque account/item/tag fields are nonempty provider strings, at most 2,048 UTF-8 bytes each. |
| Grant and cache | The helper stores one spent row per authenticated drive/migration, independent of device, save generation and app folder. Keep it for the migration's lifetime. It carries no prices or save fields. Prices, request reservations, alert crossings, home marker, private sync fields and guard are excluded from every portable format. |

Read outside bytes in a bounded, duplicate-key-detecting decoder *before* using the existing cleaner (it truncates strings at 20,000, arrays at 5,000 and nested objects at depth 10). `tracker/src/core/save.js:30–38,192–199`.
For v2 cloud use the existing wire ceiling 4 MiB minus 64 KiB. Cap expanded cloud input at 256 MiB and streamed work at that many bytes. For codes keep the 4 MiB text and 64 MiB expanded limits (`tracker/src/core/cloud.js:138–148`, `tracker/src/core/save.js:703–705`, `tracker/src/core/codec.js:98,121–134`).
Use 256 MiB as the v2 active-history/portable backup decode limit, including pending proposals. Enforce byte ceilings incrementally, cache verified nodes, budget graph work off the UI thread and cancel on resource exhaustion. Raw export streams original bytes without requiring successful replay.
Refuse an oversized write/import as a whole, with the previous save usable. Existing v1 data outside a new limit remains exportable in its original format. A migration that cannot preserve all of it leaves v1 in place.
Page creation limits are 200 watched, 500 own items and 2,000 purchases on the current trip. A valid imported save can exceed editor caps. Allow reading, editing existing entries and Undo. Refuse only a new excess entry.
For malformed inputs preserve the entire original file/response or stored bytes under a separate raw recovery key with its content digest. No lossy JSON “clean” pass, partial enrollment or arithmetic from suspect records. Offer the original for download. If local archival fails, keep the source in place and stop.

## 7. Owner choices

The tick-only default, tested option to add stock, separate erase-fix release, 30-day interval and one-time migration carry forward. A disputed selection can delay the combined view while copies of both sides are backed up.

**Older-format browsers.** The previous draft let these browsers sync with the older cloud file. The binding instruction bars updated software from writing that file.

| Option | What happens and improves | Cost, remaining risk, what you give up and confidence |
| --- | --- | --- |
| Keep the previous draft's older cloud sync by changing the instruction | Updated browsers with limited space can continue backing up automatically and exchanging changes with old versions. | Build effort is unknown. Their file stays separate from the newer save, and the earlier merge behavior still applies there. You give up the promise that updated software leaves the old cloud file alone. I am confident updated and older-format changes would remain separate, with unknown frequency. |
| Keep the instruction and support local older-format saves and files | Older data stays editable in the browser and can still move by file. Updated software leaves the old cloud copy alone. | A player has to export and import files, with unknown effort. Losing the only local copy before export can lose changes. You give up automatic cloud backup on that browser. I am confident this preserves local editing when safe storage is available. Loss odds are unknown. |
| Require full storage for every edit | Players can read and export until the browser can hold the protected save. This removes the older-format writing path. | Build effort saved is unknown. Players unable to free space can be blocked from recording progress. You give up local editing that is still possible today. I am confident this blocks more actions than the fallback, with unknown frequency. |

**Recommendation.** Keep the instruction and support local older-format saves and files. It preserves local editing and the old cloud copy. The design uses this option.

Technical: S8, S12, T21, D67, D83

**Remembering the first move.** Deleting the newer file and clearing browser data can wipe the clues that the older file was already read.

| Option | What happens and improves | Cost, remaining risk, what you give up and confidence |
| --- | --- | --- |
| Keep the previous draft's device and cloud clues | The first apparent device reads the older file with the existing sign-in setup. There is no separate lasting record to operate. | Build effort is unknown. When both clues disappear the app can repeat the read. You give up the once-only guarantee. I am confident the failure is possible. Its frequency is unknown. |
| Keep a lasting record with the sign-in service | The service remembers that the one automatic chance was used even if the newer file and every browser are cleared. Local file recovery stays available. | Hosting cost, permission and maintenance effort are unknown. A crash can spend the chance before data arrives. You give up an automatic second attempt. I am confident the rule works if the service proves the record was kept. The real service behavior is unverified. |
| Put a separate record in the player's cloud folder | The app remembers the move independently of the main file, without new service storage. | Provider setup and test effort are unknown. A player or bulk cleanup can remove both files. You give up the guarantee if both records disappear. I am confident it helps when only the main file is deleted. The odds are unknown. |
| Use a player-supplied file for every move | The player chooses a saved copy and previews what to bring in. **Recommendation.** Keep a lasting record with the sign-in service. It preserves the automatic first transfer and remembers the move after both ordinary clues are lost. The design uses this route subject to build verification.
