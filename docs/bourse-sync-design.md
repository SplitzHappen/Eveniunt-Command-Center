# Bourse · Save and sync · Version 3

Owner-requested design revision and full replacement. Authored with Codex, OpenAI GPT-6 family (`gpt-6.2-sol`).
The design and code references use public commit `4dfe0749a2938e2d6b0aad5276ba0a806e662bfc`. The pull request advanced during assignment pickup. The newer head is recorded separately.

## 1. How a device knows what happened

Each edit names what the player had seen. A deletion leaves evidence, including when older history is trimmed.
A returning phone can bring its own edits without treating a list deleted on the computer as newly added.
Replacing a character in a slot keeps the old character's stock, purchases and other records with the old identity.
A purchase counts once. Adding or using a known quantity can combine with a purchase. Typing a total may already include it, so the app asks.
The cloud replaces only the copy the app checked. Older-format browsers keep working locally and move saves by file.

## 2. Decisions

**S1. Save editions and edits.** [Rejected option: infer what happened from two snapshots or their timestamps.]
The readable shared fields are the materialization of one accepted edition. Recent transactions form a directed acyclic graph. A node records its parents and its exact logical writes. A parent is an edition the player or a validated reconciliation actually applied.
A removal is a typed tombstone. Missing legacy scope, absent field, present zero and removal are different states. A reset to a previous value is a new write.
Make one node per committed debounce burst or checked user command, including all the fields of a compound action. A node contains deltas. Idle sync, unchanged reads and repeated delivery create no node. Hold distinct tips until a join or decision dominates them. S13 cuts only a proved stable prefix.

**S2. Join histories at the path they share.** [Rejected option: use the most recent upload, choose an arbitrary common ancestor, or treat a link as a new edit of every field.]
Union validated nodes by identity and derive the maximal writers of each path. For each pair of writes to a path, discard the older one only if the newer one provably supersedes it. Equal surviving values may be displayed together. Unequal surviving values require a decision unless a rule in S4 or S6 specifies a compatible join.
Distinct seed histories need a reviewed bridge. Materialize one fully covered outcome over all represented paths: explicitly decide unequal values, including unequal absences, and explicitly adopt the origin writes for every equal value and equal recorded tombstone. Paths represented by only one source keep that source's writes. Mere absence in a source that never represented a path has no effect.
For an equal path the bridge records an **equivalence**, consisting of the exact maximal same-value write IDs in its parents. It represents those writes as one logical predecessor, with no extra competing writer. A later edit descended from any member supersedes the matched predecessor, even if its author never saw the bridge. The same applies to a deletion. A later write that changes a bridged value expressly supersedes the matched class. A bridge's actual decision between unequal writes is an ordinary write with the bridge's parents and does compete with a concurrent edit.
For a path, first respect actual causal edges. Contract only the validated same-path equivalences in the relevant ancestry. Use the transitive closure of strict supersession between the resulting classes. A new equivalence may join only incomparable, byte-equal maximal representatives in its own parent view. If independently made bridges create a cycle after contraction, **skip equivalence reduction for that path's conflict group** and offer the surviving values from the original causal graph. Keep the raw evidence. An explicit resolution over all covered originals becomes an ordinary write and hides those disputed aliases wherever that resolution dominates. Never pick a “winner” from the cycle.
Example: A and B start with tick X. Join their equal writes in M. A removes X while offline, then receives M. Its explicit removal supersedes the shared predecessor. Apply the normal removal confirmation, with no misleading “edited on the other device” choice. A real concurrent value change still requires review.
For a device behind a history cut, use the ancestry and deletion evidence in S13. For a foreign or rolled-back cloud file, or a scoped replacement, compare affected units in their declared scope. Show all unequal values and one-sided entries in that scope. Missing evidence never means removal. A truly unused device may only accept or defer; check all modules, history, pending changes, settings and character detail before offering that shortcut.

**S3. Keep valid editions while asking.** [Rejected option: an all-tips preview token, provisional stock totals, and a mutable per-key base.]
Each device and the cloud have a valid active edition and outstanding tips. Persist competing tips before showing them. A conditional cloud write can carry proposals without changing the cloud's active edition. Show local-only while transmission is unconfirmed. A third device's proposal is retained even if it has never seen the question.
A preview token binds just the conflict group: canonical affected paths, exact maximal writer IDs and values, proposed effects, and the closure of dependencies plus their observed writers, including expected absence. Dependencies include slot occupancy, children, list selection, stock receipts and any touched constraints. In a detached group bind the immutable source identity and its affected scope slice. Hash only that slice, including scoped absences, so an unrelated edit to the live document cannot invalidate the answer. Use the local epoch, account and cloud generation as context.
At commit re-read the actual current local and cloud snapshots. Recompute the group and its dependencies. If any shown input, membership or effect changed, refresh that group before accepting the answer. Unrelated local or remote edits can rebase the accepted group onto the latest heads silently. Provider preconditions still use the **current** item and tag. A failed conditional write repeats the read and dependency check before sending. Keep accepted answers in the current preview until all groups required for one valid join are answered. Unrelated edits remain durable as separate tips. The join consumes a resolved preview only after each answer still matches.
If independent answers are submitted in one transaction, each is revalidated. Unanswered groups keep their alternatives and each device's last valid edition for those groups. Independent validated edits may continue and be backed up. If a partial active edition would split a dependency group or claim a merge parent it has not applied, publish proposals only. Store no provisional count and no sync acknowledgement for an unconfirmed upload.
Freeze writes that would change a disputed group's inputs or outputs, including craft ingredients, stock outputs, hand-ins and Undo. Rejections roll back the whole command. A decision writes the chosen values or tombstones and the exact alternatives it settles. Conflicting decisions remain separate edits. Settings may offer “Answer now” during automatic sync and open the preview after sign-in or a manual request. Tracker waits until visible.

**S4. Bind records to characters and show dependent losses.** [Rejected option: permanent slot identifiers, one arbitrary merge base, or a wall-clock winner.]
`c1`–`c8` are display positions. Each actual creation allocates an immutable random 128-bit incarnation. Every owner-bound path and link uses that identity (§3). During preparation and commit resolve an offered slot through the command’s observed incarnation. A different occupant is a changed dependency. Zero active characters is valid. Orphan ticks cannot create one.
Retirement writes the old incarnation’s retired state as a lifecycle tombstone. It clears the slot or binds the new incarnation if replacement is in the same transaction. Preserve the old character’s data under that incarnation. Lists and company associations can display as unassigned while retaining the old link. A list still marked retired must not spend ordinary unassigned stock. Atelier profiles, stock, purchase receipts and records remain recoverable. The new occupant starts with its own stock and data. A late rename, tick, count, receipt or refresh for the old incarnation conflicts with retirement or stays with the retired record after approval. It can never change the replacement. The placeholder shortcut applies only to one live identity.
On the first link of independently upgraded v1 saves, propose one batch pairing same-slot characters with equal non-placeholder names and no contrary available character identifier or conflicting relationship. Summarize paired names and affected groups. The player may confirm the batch or expand and change individual proposals. Empty slots, placeholder-only matches, different or ambiguous identities, retirements and reused slots require separate review. An approved mapping aligns identity components before computing S2 path equivalences, and persists as a checked alias, not as a slot binding. Late edits follow the old incarnation alias. Purchases keep their original immutable owner IDs, resolved through that alias. An incompatible mapping is a conflict.
Preserve Lists' children and Submersibles' company, slot, submarine and voyage dependencies. For a field rule that needs a base, compute the value at each maximal common ancestor. Use it only when all agree, including scope and absence. If evidence is ambiguous, use an order-independent rule such as discovery union or ask. Preserve the applicable max-slots/min-order behavior. For proven duplicate List or target births with the same ID, sort creation digests. The smaller keeps the ID. Allocate the other a valid free ID from the domain-labelled digest of the record type, original ID, other creation digest and first free increasing salt. Persist the mapping by birth digest, including children, step links, selections, source keys and late edits. Where a birth is unproved, ask.
Before adopting an edition, show every uncovered destructive effect on participating active copies, including affected children, stock, voyages and receipts. Record approval against the exact affected writes and dependency set. Keep the receiving Tracker’s confirmation for incoming unticks. A locally loaded or erased value carries no global consent. A declined removal leaves its original edition available, with no automatic publication of the rejected effect.

**S5. Prepare deltas off-thread and keep unapplied intents.** [Rejected option: rehashing the graph inside IndexedDB or dropping an edit after two races.]
Persist an intent ID, original before-writes, dependency tokens, epoch and command payload before promising it is queued. A worker computes deltas, changed snapshot pages and digests against a checked revision. Recheck the main, guard, epoch, revision and dependencies in a short write transaction. Commit immutable new records, root pointers, revision and intent removal together. Share one node store between main and guard. See §3 for recovery and cleanup. A successful callback receives the committed edition. Page notifications only accelerate refresh.
On contention, reprepare from actual storage against the original intent. Try at most twice immediately. Then leave the durable intent pending and surface “Waiting to save”; reattempt once on a different committed revision, a reopened page or an explicit retry. Ignore self-generated queue and cleanup events, coalesce wakeups, and on focus reread the revision even if a notification was lost. No busy loop or drop. A changed input or epoch moves the item to visible “Needs review” with the original draft. Only a fresh confirmation can reapply it. A quota failure before queueing shows “Not saved” and retains the draft in that page for retry or export.
An intent retry keeps its original ID. If its apply result is unknown, check durable state for the committed ID before writing again. A purchase uses the stricter retry window in S7 and never re-arms an expired click. Its surviving draft can start a fresh, confirmed command. Replacements rotate the epoch and fence callbacks. Only the sync finalizer writes a non-null cloud receipt. Refresh and backup acknowledgements update their own device fields and never regress another writer’s data.

**S6. Separate typed totals, relative changes and receipts.** [Rejected option: merging displayed totals or treating every stock gesture as an absolute count.]
Group by canonical owner incarnation and item. For each quality, visible stock equals own stock plus active credits. No credits for collectables. Missing visible stock is zero. Own stock may be negative. Use exact integer arithmetic and reject any materialization outside 0–999,999. Keep existing untouched v1 shapes and apply existing stock constraints per group. One immutable receipt ID counts once. Cancellation changes its state and preserves its body.
A typed total writes an absolute reset, with the entered total, computed own part and observed receipt-state frontier. A Lists ±, ordinary Bought, Made or hand-in records signed own-part deltas, the exact before/after difference the existing validated command actually applied. Record the entire action, including outputs, ingredients, target and step changes. A Bourse purchase/Undo changes its identified receipt and leaves own stock alone. A Lists Undo of a relative command may record the exact checked inverse once, with a reference to the original command; undoing an absolute reset is another checked reset. [Stock commands](https://github.com/SplitzHappen/Eveniunt-Command-Center/blob/4dfe0749a2938e2d6b0aad5276ba0a806e662bfc/tracker/command-center/src/lists/store.js#L295-L415).
For each quality reduce from its latest comparable seed/reset plus distinct relative operations that descend from it. Preserve each delta's immutable operation ID through merge. An observed delta is included in the reset and counted once. An unobserved concurrent relative operation and reset ask if their orders could change the result. Competing resets, or an absolute edit concurrent with a receipt activation/cancellation/reactivation in the same owner/item group, require preview even when there is only one reset. A typed 50 concurrent with a purchase of 40 from 10 offers 50 with the purchase included or 90 with it separate. A typed edit that actually saw the receipt does not ask about that receipt.
Relative changes and receipt changes commute when dependencies still hold and the resulting **whole** action is legal. From 10, consuming 3 on one device and crediting 40 on the other gives 47, preserving all effects of the craft. Two relative spends that overdraw together, or a concurrent change to a craft's recipe, target, owner, hand-in or shared coupled output, require an intact-action preview. Never silently re-run caps, stock allocation or ingredient substitution against later data. An attempted no-op stores no delta. A conflict holds both complete valid editions. The chosen result records cancelled states and the exact original operation IDs it absorbed.

**S7. Bind a tick to what the player bought.** [Rejected: inferring a purchase from a change in demand or crediting each selected list for the entire row.]
Default to “Tick only”. With “Also add to I have in Lists”, allocate the purchased amount across the displayed owners using the plan's stable share order. Verify the selected lists, quantities, per-owner source targets, trip and existing marks inside the write.
Record each owner's actual purchase and actual credit. Own trip items always credit zero. At the cap, show the purchased and accepted quantities separately. From 999,990 a purchase of 40 records 40 bought, 9 credited, and 31 uncredited. If any Lists part refuses, commit none and offer a separate tick-only action.
For a combined row allocate in the order `c1…c8,u,x`, each limited to its outstanding need. Quantities beyond the outstanding need require the player to edit the purchase before recording it. Generate the purchase IDs once before dispatch. Retry only that command in its original page for at most two minutes and three attempts. Read the receipt, tombstone or local completion record before retrying. An unknown result after expiry requires a fresh view.
A purchase stays bound to the exact wanted items and amounts behind the displayed need. Subtract the uncredited part once. A different source, unexpected need, or incompatible check mark displays “To check” and excludes the row from a spending total.
For an own item, the remaining quantity is its trip quantity less the sum of active purchases, floored at zero. For a Lists row, consider only this trip, owner, item and quality. Use the causally latest active purchase/check anchors. All simultaneous latest anchors must agree on the source fingerprint and expected need after their own credit (`of − cr`). If that equals the actual current need, subtract the sum of active uncredited units (`n − cr`) once, with a floor of zero. Otherwise keep the marks and show “To check”. No display count participates in a stock write.
“Still count” writes a check against the current sources. Removing an uncredited mark requires confirmation. Undo of a credited purchase verifies the whole action and current stock, subtracts the recorded credit only if enough remains, and records the cancellation.
Allocate a trip on the first add, tick or shopping-list copy in the same write. “New trip” creates a fresh ID, clears only this trip's own items and uncredited marks after confirmation, and keeps previous credits and their Undo available.
Two offline starts get different IDs. Ask which trip to display. Keep the other trip and its own quantities accessible. A change of selection or current trip never cancels a receipt.
Hide the credit switch automatically when its build tests fail. Retain the reader and indivisible stock-group guard in the off build. With existing credit history, display/export it and refuse stock-changing actions or divergent merges for that group with an explanation.
Tick-only still works for unblocked rows. Never apply a cached `lists` preference as a grant of credit in the off build. A credit-enabled build can finish a held decision.

**S8. Use a separate cloud file and conditional writes.** [Rejected: blind path replacement, a best-effort create followed by a read, or a tag unrelated to the downloaded bytes.]
The legacy file is `eveniunt-command-center.json`. The v2 save uses `eveniunt-command-center-v2.json` in the app folder. The updated app has no writer for the old path, including its v1 fallback.
Fetch metadata and content for the same authenticated drive and item. Use a version-specific read, or bracket the body read by metadata reads with the same item ID and exact opaque `eTag`. Reject mismatches, missing tags and incomplete bodies.
A missing item is distinct from invalid JSON, an unsupported future version, access refusal and a failed download. A future version gets a reload notice. Only a proven name lookup miss can enter creation.
Reject a renamed or moved item, or a name now bound to a different item. The version-rising build must verify the provider also invalidates the item precondition on a rename/move that could redirect a pending replacement. Use a provider route documented to fail if the name exists *at final creation*. A candidate is a Graph upload session naming the item with conflict behavior `fail`. The build must prove the chosen route and its exact final request.
Keep create disabled until the documentation and ten refused creates against an existing file on personal OneDrive, with byte comparisons, are recorded. Test simultaneous finalization and disabled behavior. The version-rising release waits for that evidence.
Replace by item ID with the exact strong provider precondition (`If-Match` with the observed tag). Never retry by path or with a missing or wildcard tag. Conflict, missing item or changed account starts a fresh read and preview.
After every write require the expected item ID, the new tag and a stable read-back of the exact expected envelope identity/content. An ambiguous reply advances nothing. Rediscover by name and verify the intended item before accepting a later observation.
After a create collision, inspect and merge the winner. When the file vanished, create only under the verified condition. Preserve local proposals and start a fresh file generation. The old cloud file is never a repair source.
The file generation changes on create and damaged-copy overwrite. A generation or item change breaks the local link regardless of counters. Within a generation use actual parent containment, never an upload count, to establish ancestry.

**S9. Reserve once and consume once in the sign-in helper.** [Rejected option: an eventually consistent check-then-write or retrying authorization to read the old file.]
The current helper trades token responses for device handles and retains refresh tokens, not account identity. Keep its device store. Under the existing allowed-origin and valid device-handle checks, a new POST `/legacy-read/claim` accepts `{device,phase,generation}` with phase `reserve/consume` and a random 32-hex generation. Derive the drive from the Microsoft access token refreshed by the helper. Do not accept caller-supplied drive IDs or credentials. [Current helper](https://github.com/SplitzHappen/Eveniunt-Command-Center/blob/4dfe0749a2938e2d6b0aad5276ba0a806e662bfc/tracker/helper/worker.js#L27-L83) · [Current binding](https://github.com/SplitzHappen/Eveniunt-Command-Center/blob/4dfe0749a2938e2d6b0aad5276ba0a806e662bfc/tracker/helper/wrangler.toml#L12-L15).
Both helper and browser use `GET /v1.0/me/drive/special/approot?$select=id,parentReference` under the existing personal app-folder permission. Require the folder item and its `parentReference.driveId`. For this personal-drive migration accept only 1–16 ASCII hex characters, lowercase and left-pad to 16, then hash UTF-8 `bourse-legacy-read/personal-drive/v1`, a zero byte, and the normalized value with SHA-256. Compare the same canonical key across reserve, conditional creation and consume. Refuse missing, unsupported or changed identity. The normalization and uniqueness for the supported personal IDs are release checks, not a claim about current Microsoft responses. Test casing/leading-zero variants, two distinct accounts, existing permission and sign-in changes. [Microsoft app-folder API](https://learn.microsoft.com/en-us/graph/onedrive-sharepoint-appfolder) · [Parent reference](https://learn.microsoft.com/en-us/graph/api/resources/itemreference?view=graph-rest-1.0).

The builder ships `tracker/helper/migrations/0001_legacy_read_claims.sql`. The non-expiring row holds one reservation plus its one-way consumed bit per canonical drive. Bind parameters in D1. Use the primary database for any read after a write.

```sql
CREATE TABLE legacy_read_claims (
    drive_key TEXT NOT NULL PRIMARY KEY CHECK (length(drive_key) = 64),
    generation TEXT NOT NULL CHECK (length(generation) = 32),
    consumed INTEGER NOT NULL DEFAULT 0 CHECK (consumed IN (0, 1))
) WITHOUT ROWID;
```

```sql
INSERT INTO legacy_read_claims (drive_key, generation) VALUES (?1, ?2)
ON CONFLICT (drive_key) DO NOTHING;
SELECT generation, consumed FROM legacy_read_claims WHERE drive_key = ?1;
UPDATE legacy_read_claims SET consumed = 1
WHERE drive_key = ?1 AND generation = ?2 AND consumed = 0;
```

Reserve uses the insert and primary-consistent read as one D1 batch with bind parameters. Matching generation and `consumed=0` returns `reserved`, including on retry. A different generation or consumed row returns `spent`. The retry grants permission to continue the original create attempt only. A separate consume uses the conditional update. Only an acknowledged statement changing exactly one row returns `read-once`. Zero is `spent`. Errors, missing identity or uncertain responses authorize no read. Prove the actual API result metadata and consistency in T28. The helper never downloads user saves.
When create-only is verified and the v2 name is genuinely absent, persist the original generation, guarded attempt and account before reserve. If the reserve reply is lost, retry the **same** generation under the same account/epoch. Competing devices reread v2 and may sync its winner. A known-spent device can use its own data in a create-only recovery if the file still does not exist. An uncertain store response holds initial creation. Ordinary sync of an existing v2 file needs no D1 request.
Only the reserved attempt with an acknowledged create and stable read-back of its matching pending envelope can consume. A crash or context change after consume cannot repeat the request. Spend the positive receipt in memory immediately before starting a single logical legacy content request, with its provider redirect and no automatic retry. A lost consume acknowledgement is conservative: no automatic legacy read. After a successful staging commit, retries use local staged bytes. A reserved attempt that loses create gets no read. Deletion or replacement of v2, sign-out, or local storage loss never resets the D1 record.
Treat the one staged legacy body as an independent scoped source. It has no trustworthy bound merge base. Preview one-sided and unequal groups explicitly, with no bulk “take cloud” on a used device. Reconcile against the latest v2 copy. A missing old file marks `seed=none`, a durable accepted/staged source marks `imported`, and acknowledged continued recovery marks `manual`. Final markers never reopen. Settings can inspect a player-supplied older export locally. Updated software never writes the old file.
Keep the original database and key scheme. Failed or missing bindings stop migration claims. If the database was replaced or rewound and continuity cannot be proved, keep automatic legacy reads disabled and use file recovery. A database restored to an earlier valid state can look healthy. The owner disables claims before any administrative restore. Existing v2 sync stays available.

**S10. Separate local durability from a cloud acknowledgement.** [Rejected: a mutable sync base in page memory and updating it before the merged data lands.]
At sync start flush the initiating page's intended edits, read the guarded store, then capture its epoch, revision, active edition, tips, drive binding and a fresh attempt ID. Settings uses the full stored document even with zero characters.
Before making a request that can change OneDrive, durably record the expected item/tag (or create-only name), candidate identity and attempt. Allocate the new revision before committing the preparation. Store that post-preparation revision in the attempt and return it to the caller. A preview still binds its relevant values and dependencies under S3. The upload attempt separately binds its post-staging revision. Re-read guard and tokens immediately before dispatch. Restore, replacement, or a changed account cancels a prepared attempt before it is sent. Serialize this last check and dispatch with local replacement.
One implementation is a short transaction covering the main store. Within it, compare tokens and synchronously initiate the prepared fetch within the final read callback. Stage and hash the body before that callback. Never hold an IndexedDB transaction awaiting network I/O.
On response, recheck the account, attempt, epoch and guard in a fresh write. Install exactly the acknowledged save/receipt together. If only ordinary edits intervened, retain their branch and reconcile from the actual stored edition. The receipt points to exactly the cloud active and tips last witnessed. It never claims that an unadopted cloud edition has been applied locally. Never run a silent default-choice second merge.
A changed epoch or recovery state discards the callback. An in-flight HTTP request may already have arrived. Show an unconfirmed attempt until a fresh stable read establishes its outcome. Its item/tag condition protects intervening cloud writes. Local Restore always works offline.
A lost response, quota failure after upload, partial identity or superseded attempt cannot mark the device synced. On restart read the cloud again before sending. Identical verified content needs no upload. Keep a confirmed backup time separate from a completed reconciliation.
For damaged bytes, first offer download, then ask explicitly to replace the displayed copy with this device's checked edition. Bind consent to exact old bytes/identity, local revision, account and epoch. Refuse unsupported future formats, absent tags and unstable reads.
If another device repaired it, read and merge that sound copy. An exact return of older valid cloud bytes can have the same item and generation. Compare the fresh graph with the last confirmed active edition **and every then-confirmed tip**. A valid S13 cut may account for prior active/tip IDs in its checked covered index. Pin the last verified index with the local receipt and require its IDs to remain covered or retained. Missing acknowledged evidence otherwise breaks the link. An exact body match or proved containment allows normal comparison. A confirmed overwrite starts a new generation with no authority from the damaged file. Retain validated pending local editions. Other devices compare afresh. A normal cut uses S13’s covered-index route. A damaged-copy overwrite cannot use it.

**S11. Release the erase fix first and keep a local guard.** [Rejected: relying on a cache expiry date, or writing the safety copy in a later request.]
At the real post-module-moves baseline freeze the built files as `old0`. Release only the Tracker erase fix and rebuilt bundles as `old`. Record when the fixed website actually went live.
In that fix validate inside the erase transaction. On unreadable/newer data refuse with the reason, offer rescue and keep the screen open. On readable v1 or genuine first use preserve the existing Tracker-only meaning. Never clear page state until commit.
At least 30 full days must elapse from live publication before the version rises. Recheck every writer on the real baseline. A second old destructive writer needs a remedy, tests and the corresponding protection interval before the rise.
Before the first guarded write persist and verify the storage-home marker. Atomically write main, its revision, independent guard snapshot roots and its matching revision in the same IndexedDB store. Keep immutable graph nodes separately under S5. Include device state needed to recover proposals.
Check the two headers and revisions on each read and inside each write transaction. Verify referenced snapshot pages off-thread as they are loaded. Reuse already verified immutable records on ordinary edits. A missing or mismatched record stops the operation. A valid guard with missing, unreadable, lower-version or mismatched main enters recovery. A v2 main with missing/broken guard is also a recovery case. Never silently bless it or create a blank save.
Show both dates, sizes and exportable originals. Restore copies valid guard contents. Keep requires a separately checked, readable main and a second confirmation. Archive displaced raw bytes before installing the selected content. Missing/malformed content cannot be chosen as the new save.
Compare *both raw identities and revisions* inside the action. Missing-revision and missing-data states are distinct. Stale dialog, new generation, unreadable future version or quota failure leaves storage untouched. Redisplay current state. Two invalid copies permit raw export and explicit recovery from a valid supplied backup.
While recovery is pending, no ordinary write, legacy read, upload, cleanup or sync finalizer runs. A replacement rotates the epoch even when the data is equal. S12 decides which history and cloud witness can safely carry forward.
Show “Reload the page to update” in updated refusal paths. Ship the instruction to reload **every** open page online. Frozen binaries keep their observed messages. A cached Atelier can appear usable while saving nothing to the shared store.
A guard recovers the last guarded save. Clearing the entire origin can remove both copies. A separate backup or a verified cloud copy is then the recovery source.

**S12. Fix the storage home and limit replacement to its scope.** [Rejected option: silently fall back to a different store, replace from an unchecked file, or detach every module after a partial restore.]
Persist and verify the IndexedDB home marker before migration. Carry a real fallback v1 save across under same-origin exclusion and compare its source bytes again. Keep the source. If accessible stores differ or home is uncertain, show the competing exportable copies and hold writes. Once the home is recorded, a transient failure never selects localStorage or memory.

Show “Local older-format save only. To move this save, use a backup file.” Recheck stored version and serialization on each write. Without safe cross-tab exclusion, read and export survive. An unguarded older app tab is outside that exclusion. Memory mode visibly says “not saved”.
On quota, reclaim unreachable records first (§3). If space is still short, clear the capped price cache (60,000 records), wait up to five seconds for confirmation, then retry once against current state. Keep request gates, save and guard. Show storage use and manual cache clearing.
For backup/code, validate first, show scope and losses, archive the displaced bytes, then commit the selected materialization. Scope comes from actually represented sections and groups in the format, including explicit empty sections. Tracker-only files and go-back touch the selected Tracker and character fields. Preserve unrepresented modules and ancestry. Any character mapping that would also affect a module's association requires showing that dependency before approval. Existing unrelated sections retain their write IDs and dependencies.

A single local replace node records its finite scope, checked writes and the fact that this was a local replacement. It inherits the old tip for every untouched path. It emits a tombstone only for a shown local value that was actually replaced. For the represented scope, force review against live cloud differences, **including remote-only entries within that scope**, even if graph ancestry would otherwise choose the loaded version. No authority comes from a file's device metadata or consent history. If both sides agree, verify equality and acknowledge it without sending data loss. A scoped, causally recorded reconciliation closes the comparison; retries and staging preserve it.

Its historical active node never grants local authority and can never disappear from a late preview merely because that old node is an ancestor in the cloud. **S13. Trim history at a settled boundary and carry proof forward.** [Rejected option: swap to an unrelated seed or expire deletion records by time.]
Measure the compressed wire body for every send. Use 3 MiB as the soft threshold and 4 MiB minus 64 KiB (4,128,768 bytes) as the hard ceiling. Initial soft budget: 1.5 MiB for the live snapshot/boundary, 0.75 MiB for recent edits and 0.75 MiB for old identities and deletions. A typical small edit is budgeted at 180 wire bytes, estimated from 80 bytes of digest/parent/nonce entropy before base64 plus framing and operation data. A packed 32-byte old node ID costs about 43 wire bytes. Both estimates exclude variable tombstone, frontier and large-record costs. Measure them. Idle sync adds no node. A failed soft cut is a hold at the hard ceiling, without sending oversize bytes.
Cut only on proved related cloud history under S8. Find a settled single tip covering the main, cloud and all known proposals. Choose the most recent eligible settled ancestor C that leaves at least 512 committed nodes after it. Remove exactly C and its ancestors. Keep the descendant graph byte for byte, including original IDs and parents. Every retained parent must be C or another retained node. References to old path writers need the exact frontier/equivalence evidence at C. An unresolved alternate branch, bypassing parent or reference that cannot be replayed without removed facts makes that boundary ineligible. If none is eligible, or the resulting envelope does not shrink, defer. This admits a settled suffix with internal forks and joins.
The checkpoint keeps the boundary node ID, its checked materialized frontier with original path-writer identities (including approved equivalences), and an **exact** cumulative index of covered node IDs from the prefix, including the boundary. Keep typed tombstones with their paths, applying write IDs and exact superseded write IDs, including destructive dependency effects. Keep retirement tombstones, identities/aliases, operation IDs needed for stock or retry deduplication and immutable receipt bodies with cancellation state. Keep tombstone evidence even after an intentional re-add. Store metadata in canonical sorted arrays with shared dictionaries and packed hashes. No Bloom filter, time-based expiry or unproved membership. This replaces old graph bodies, not deletion evidence.
A cut keeps the same file generation. Validate the old graph, checkpoint bytes and replay of the unchanged suffix with the **same** active state/dependency frontier before publishing conditionally. Preserve a compressed local recovery archive or verify an explicitly chosen full export of the pre-cut graph first. Recheck before adoption. If a local edit raced the upload, keep it under its original tip; reconcile via the returning-device rule. Archives do not keep old snapshot pages alive. Confirmed cloud/guard roots, unfinished work and verified archives are protected from cleanup. If proof or archive cannot fit, pause cloud sync while keeping local and file recovery usable.
**Returning device.** In the same verified account/item/generation, locate the latest comparable common ancestor in the local graph and the retained graph or covered-index. A device sitting on an indexed ancestor of the cut, with no unseen work, takes the normal related update, including ordinary receiving confirmation for known removals. It is not sent through a full independent-copy merge. Recognize a live value with a matching superseded writer as “Deleted on another device”, with no automatic upload of that older value. Keep/restore requires the player to explicitly approve a **new** write showing this deletion. A decline leaves that local edition available without recreating the cloud value.
If the device has unpublished descendants of an indexed ancestor, discard no unseen operation. Determine covered vs unseen by original ID. Reconstruct the local common base and both changed frontiers. Compare per-path writer evidence and the full dependencies against the current cloud. Use the covered index to prove absence of unseen work or eligibility of a common ancestor. Membership alone never states which writer a tombstone superseded. Use writer identity and approved equivalences, including recorded absence, rather than equality of displayed values. Reapply unseen operations only against unchanged dependencies or the compatible joins in S4/S6. A changed dependency or overlapping remote edit/deletion asks for that group. If distinct maximal bases cannot be reconciled, keep the affected groups pending. Join writes actual chosen changes and records absorbed original IDs so retries cannot reapply a stock delta or credit. Retain the older operation evidence until acknowledgement and preserve it in the recovery archive. A local branch with only covered operations is never resent as new, including after a lost reply.
For a genuinely independent or unproved copy, keep the scoped comparison of S2. Still label exact tombstone matches as deleted elsewhere, and show separately when a deletion exists for the same path with a different writer. Only individual explicit re-add consent can revive a known deletion. An overwritten or rolled-back file must establish its own link. Only normal cuts in a proved generation use the covered-index route.
Proof grows more slowly than full nodes but does grow indefinitely. At 100 distinct edits/day an exact ID index alone can add about 1.5 MiB/year if all are distinct and retired. Large saves or heavily edited histories may eventually need local saves/backup transfer. Report breakdown and pause at the hard limit. Never erase deletion or ancestry evidence to make a send fit.

## 3. Data shapes and validation

**Formats.** Keep both legacy tag families readable, plus native v1 files, Tracker-only v1 files and `EVT1-/EVT2-`. Local `main` is a v2 header `{app:"eveniunt-command-center",v:2,updated,epoch,snapshot,active,tips}`. New readers materialize the compatible fields from disk pages. The header fences old writers. Native backup v2 uses `{app:"eveniunt-command-center",kind:"backup",v:2,saved,save:{chars,modules,history}}`. `EVT3-` adds `history` to its compressed compatibility payload. Require it and validate the entire payload. Cloud outer `{app:"eveniunt-completionist-tracker",v:3,format:"deflate-raw+base64",data}` wraps `{app:"eveniunt-command-center",v:2,generation,seed,chars,modules,history}`. Cloud generation is 32 random hex digits and `seed` is `pending/imported/none/manual`. Cloud and local format versions are distinct from the Tracker UI version. Preserve private device data only locally.
