# Bourse · Save and sync · Version 5

Owner-requested full design revision. Authored with Codex, OpenAI GPT-6 family (`gpt-6.2-sol`).
Public evidence and source lines are pinned to `8582f59ed953e43eff29d014177eab2b8e99f63d`. The separate state record gives the observed pull request head.

## 1. How a device knows what happened

Edits name what the player had seen. Removals leave a record in the change log.
The log has a space limit. Trimming it leaves every saved character, tick, list, stock figure and purchase intact.
A returning device can accept cloud changes together when its saved copy proves it made no local edits. Where evidence is missing or both sides changed a group, the app asks about that group.
Each purchase counts once. A typed total may already include a purchase made on another device, so the app asks when it cannot tell.
Cloud writes replace only the copy the app checked. A reused character slot starts with a separate identity and separate stock.

## 2. Decisions

**S1. Save editions and edits.** [Rejected option: infer what happened from two snapshots or their timestamps.]
The readable shared fields are the materialization of one accepted edition. Recent transactions form a directed acyclic graph. A node records its parents and its exact logical writes. A parent is an edition the player or a validated reconciliation actually applied.
A removal is a typed tombstone. Missing legacy scope, absent field, present zero and removal are different states. A reset to a previous value is a new write.
Make one node per committed debounce burst or checked user command, including all the fields of a compound action. A node contains deltas. Idle sync, unchanged reads and repeated delivery create no node. Hold distinct tips until a join or decision dominates them. S13 only cuts prefixes of accepted history.

**S2. Join histories at the path they share.** [Rejected option: use the most recent upload, choose an arbitrary common ancestor, or treat a link as a new edit of every field.]
Union validated nodes by identity and derive the maximal writers of each path. For each pair of writes to a path, discard the older one only if the newer one provably supersedes it. Equal surviving values may be displayed together. Unequal surviving values require a decision unless a rule in S4 or S6 specifies a compatible join.
Distinct seed histories need a reviewed bridge. Materialize one fully covered outcome over all represented paths: explicitly decide unequal values, including unequal absences, and explicitly adopt the origin writes for every equal value and equal recorded tombstone. Paths represented by only one source keep that source's writes. Mere absence in a source that never represented a path has no effect.
For an equal path the bridge records an **equivalence**, consisting of the exact maximal same-value write IDs in its parents. It represents those writes as one logical predecessor, with no extra competing writer. A later edit descended from any member supersedes the matched predecessor, even if its author never saw the bridge. The same applies to a deletion. A later write that changes a bridged value expressly supersedes the matched class. A bridge's actual decision between unequal writes is an ordinary write with the bridge's parents and does compete with a concurrent edit.
For a path, first respect actual causal edges. Contract only the validated same-path equivalences in the relevant ancestry. Use the transitive closure of strict supersession between the resulting classes. A new equivalence may join only incomparable, byte-equal maximal representatives in its own parent view. If independently made bridges create a cycle after contraction, **skip equivalence reduction for that path's conflict group** and offer the surviving values from the original causal graph. Keep the raw evidence. An explicit resolution over all covered originals becomes an ordinary write and hides those disputed aliases wherever that resolution dominates. Never pick a “winner” from the cycle.
Example: A and B start with tick X. Join their equal writes in M. A removes X while offline, then receives M. Its explicit removal supersedes the shared predecessor. Apply the normal removal confirmation, with no misleading “edited on the other device” choice. A real concurrent value change still requires review.
For a device behind the kept log or unknown to the account, use S13’s labelled comparison and its verified unchanged-path shortcut. For a foreign or rolled-back cloud file, or a scoped replacement, compare affected units in their declared scope. Show all unequal values and one-sided entries in that scope. Missing evidence never means removal. A truly unused device may only accept or defer; check all modules, history, pending changes, settings and character detail before offering that shortcut.

**S3. Keep valid editions while asking.** [Rejected option: an all-tips preview token, provisional stock totals, and a mutable per-key base.]
Each device and the cloud have a valid active edition and outstanding tips. Persist competing tips before showing them. A conditional cloud write can carry proposals without changing the cloud's active edition. Show local-only while transmission is unconfirmed. A third device's proposal is retained even if it has never seen the question.
A preview token binds just the conflict group: canonical affected paths, exact maximal writer IDs and values, proposed effects, and the closure of dependencies plus their observed writers, including expected absence. Dependencies include slot occupancy, children, list selection, stock receipts and any touched constraints. In a detached group bind the immutable source identity and its affected scope slice. Hash only that slice, including scoped absences, so an unrelated edit to the live document cannot invalidate the answer. Use the local epoch, account and cloud generation as context.
At commit re-read the actual current local and cloud snapshots. Recompute the group and its dependencies. If any shown input, membership or effect changed, refresh that group before accepting the answer. Unrelated local or remote edits can rebase the accepted group onto the latest heads silently. Provider preconditions still use the **current** item and tag. A failed conditional write repeats the read and dependency check before sending. Keep accepted answers in the current preview until all groups required for one valid join are answered. Unrelated edits remain durable as separate tips. The join consumes a resolved preview only after each answer still matches.
If independent answers are submitted in one transaction, each is revalidated. Unanswered groups keep their alternatives and each device's last valid edition for those groups. Independent validated edits may continue and be backed up. If a partial active edition would split a dependency group or claim a merge parent it has not applied, publish proposals only. Store no provisional count and no sync acknowledgement for an unconfirmed upload.
Freeze writes that would change a disputed group's inputs or outputs, including craft ingredients, stock outputs, hand-ins and Undo. Rejections roll back the whole command. A decision writes the chosen values or tombstones and the exact alternatives it settles. Conflicting decisions remain separate edits. Settings may offer “Answer now” during automatic sync and open the preview after sign-in or a manual request. Tracker waits until visible.

**S4. Bind records to characters and show dependent losses.** [Rejected option: permanent slot identifiers, one arbitrary merge base, or a wall-clock winner.]
`c1`–`c8` are display positions. Each actual creation allocates an immutable random 128-bit incarnation. Every owner-bound path and link uses that identity (§3). During preparation and commit resolve an offered slot through the command’s observed incarnation. A different occupant is a changed dependency. Zero active characters is valid. Orphan ticks cannot create one.
Retirement writes the old incarnation’s retired state as a lifecycle tombstone. It clears the slot or binds the new incarnation if replacement is in the same transaction. Preserve the old character’s data under that incarnation. Lists and company associations can display as unassigned while retaining the old link. A list still marked retired must not spend ordinary unassigned stock. Atelier profiles, stock, purchase receipts and records remain recoverable. The new occupant starts with its own stock and data. A late rename, tick, count, receipt or refresh for the old incarnation conflicts with retirement or stays with the retired record after approval. It can never change the replacement. The placeholder shortcut applies only to one live identity.
On a first link or any later slot clash, propose one batch pairing same-slot characters with equal non-placeholder names and no contrary available character identifier or conflicting relationship. Summarize paired names and affected groups. The player may confirm the batch or expand and change individual proposals. Empty slots, placeholder-only matches, contradictory identities or relationships, and a match to a retired incarnation require separate review. Concurrent new or re-added incarnations can be paired only by explicit approval for the two live candidates. Never pair a new character with a retired one by matching the name. An approved mapping aligns identity components before computing S2 path equivalences, and persists as a checked alias, not as a slot binding. Late edits follow the old incarnation alias. Purchases keep their original immutable owner IDs, resolved through that alias. An incompatible mapping is a conflict.
Preserve Lists' children and Submersibles' company, slot, submarine and voyage dependencies. For a field rule that needs a base, compute the value at each maximal common ancestor. Use it only when all agree, including scope and absence. If evidence is ambiguous, use an order-independent rule such as discovery union or ask. Preserve the applicable max-slots/min-order behavior. For proven duplicate List or target births with the same ID, sort creation digests. The smaller keeps the ID. Allocate the other a valid free ID from the domain-labelled digest of the record type, original ID, other creation digest and first free increasing salt. Persist the mapping by birth digest, including children, step links, selections, source keys and late edits. Where a birth is unproved, ask.
Before adopting an edition, show every uncovered destructive effect on participating active copies, including affected children, stock, voyages and receipts. Record approval against the exact affected writes and dependency set. Keep the receiving Tracker’s confirmation for incoming unticks. A locally loaded or erased value carries no global consent. A declined removal leaves its original edition available, with no automatic publication of the rejected effect.

**S5. Prepare deltas off-thread and keep unapplied intents.** [Rejected option: rehashing the graph inside IndexedDB or dropping an edit after two races.]
Persist an intent ID, original before-writes, dependency tokens, epoch and command payload before promising it is queued. A worker computes deltas, changed snapshot pages and digests against a checked revision. Recheck the main, guard, epoch, revision and dependencies in a short write transaction. Commit immutable new records, root pointers, revision and intent removal together. Share one node store between main and guard. See §3 for recovery and cleanup. A successful callback receives the committed edition. Page notifications only accelerate refresh.
On contention, reprepare from actual storage against the original intent. Try at most twice immediately. Then leave the durable intent pending and surface “Waiting to save”; reattempt once on a different committed revision, a reopened page or an explicit retry. Ignore self-generated queue and cleanup events, coalesce wakeups, and on focus reread the revision even if a notification was lost. No busy loop or drop. A changed input or epoch moves the item to visible “Needs review” with the original draft. Only a fresh confirmation can reapply it. A quota failure before queueing shows “Not saved” and retains the draft in that page for retry or export.
An intent retry keeps its original ID. If its apply result is unknown, check durable state for the committed ID before writing again. A purchase uses the stricter retry window in S7 and never re-arms an expired click. Its surviving draft can start a fresh, confirmed command. Replacements rotate the epoch and fence callbacks. Only the sync finalizer writes a non-null cloud receipt. Refresh and backup acknowledgements update their own device fields and never regress another writer’s data.

**S6. Separate typed totals, relative changes and receipts.** [Rejected option: merging displayed totals or treating every stock gesture as an absolute count.]
Group by canonical owner incarnation and item. For each quality, visible stock equals own stock plus active credits. No credits for collectables. Missing visible stock is zero. Own stock may be negative. Use exact integer arithmetic and reject any materialization outside 0–999,999. Keep existing untouched v1 shapes and apply existing stock constraints per group. One immutable receipt ID counts once. Cancellation changes its state and preserves its body.
A typed total writes an absolute reset, with the entered total, computed own part and observed receipt-state frontier. A Lists ±, ordinary Bought, Made or hand-in records signed own-part deltas, the exact before/after difference the existing validated command actually applied. Record the entire action, including outputs, ingredients, target and step changes. A Bourse purchase/Undo changes its identified receipt and leaves own stock alone. A Lists Undo of a relative command may record the exact checked inverse once, with a reference to the original command; undoing an absolute reset is another checked reset. [Stock commands](https://github.com/SplitzHappen/Eveniunt-Command-Center/blob/8582f59ed953e43eff29d014177eab2b8e99f63d/tracker/command-center/src/lists/store.js#L295-L415).
For each quality reduce from its latest comparable seed/reset plus distinct relative operations that descend from it. S13 preserves the active reset identity and typed/relative distinction across a cut. Preserve each delta's immutable operation ID through merge. An observed delta is included in the reset and counted once. An unobserved concurrent relative operation and reset ask if their orders could change the result. Competing resets, or an absolute edit concurrent with a receipt activation/cancellation/reactivation in the same owner/item group, require preview even when there is only one reset. A typed 50 concurrent with a purchase of 40 from 10 offers 50 with the purchase included or 90 with it separate. A typed edit that actually saw the receipt does not ask about that receipt.
Relative changes and receipt changes commute when dependencies still hold and the resulting **whole** action is legal. From 10, consuming 3 on one device and crediting 40 on the other gives 47, preserving all effects of the craft. Two relative spends that overdraw together, or a concurrent change to a craft's recipe, target, owner, hand-in or shared coupled output, require an intact-action preview. Never silently re-run caps, stock allocation or ingredient substitution against later data. An attempted no-op stores no delta. A conflict holds both complete valid editions. Decisions record real receipt states and the absorbed operation IDs in the bounded journal. A late device without a proved base cannot replay a relative operation or infer a receipt cancellation from absence.

**S7. Bind a tick to what the player bought.** [Rejected: inferring a purchase from a change in demand or crediting each selected list for the entire row.]
Default to “Tick only”. With “Also add to I have in Lists”, allocate the purchased amount across the displayed owners using the plan's stable share order. Verify the selected lists, quantities, per-owner source targets, trip and existing marks inside the write.
Record each owner's actual purchase and actual credit. Own trip items always credit zero. At the cap, show the purchased and accepted quantities separately. From 999,990 a purchase of 40 records 40 bought, 9 credited, and 31 uncredited. If any Lists part refuses, commit none and offer a separate tick-only action.
For a combined row allocate in the order `c1…c8,u,x`, each limited to its outstanding need. Quantities beyond the outstanding need require the player to edit the purchase before recording it. Generate the purchase IDs once before dispatch. Retry only that command in its original page for at most two minutes and three attempts. Read the receipt, tombstone or local completion record before retrying. An unknown result after expiry requires a fresh view.
A purchase stays bound to the exact wanted items and amounts behind the displayed need. Subtract the uncredited part once. A different source, unexpected need, or incompatible check mark displays “To check” and excludes the row from a spending total.
For an own item, the remaining quantity is its trip quantity less the sum of active purchases, floored at zero. For a Lists row, consider only this trip, owner, item and quality. Use the causally latest active purchase/check anchors. All simultaneous latest anchors must agree on the source fingerprint and expected need after their own credit (`of − cr`). If that equals the actual current need, subtract the sum of active uncredited units (`n − cr`) once, with a floor of zero. Otherwise keep the marks and show “To check”. No display count participates in a stock write.
“Still count” writes a check against the current sources. Removing an uncredited mark requires confirmation. Undo of a credited purchase verifies the whole action and current stock, subtracts the recorded credit only if enough remains, and records the cancellation.
Allocate a trip on the first add, tick or shopping-list copy in the same write. “New trip” creates a fresh ID, clears only this trip's own items and uncredited marks after confirmation, and keeps previous credits and their Undo available.
Two offline starts get different IDs. Ask which trip to display. Keep the other trip and its own quantities accessible. A change of selection or current trip never cancels a receipt.
Hide the credit switch automatically when its build tests fail. Retain the reader and indivisible stock-group guard in the off build. With existing credit history, display/export it and refuse stock-changing actions or divergent merges for that group with an explanation.
Tick-only still works for unblocked rows. Never apply a cached `lists` preference as a grant of credit in the off build. A credit-enabled build can finish a held decision.

**S8. Use a separate cloud file and conditional writes.** [Rejected: blind path replacement, a best-effort create followed by a read, or a tag unrelated to the downloaded bytes.]
The legacy file is `eveniunt-command-center.json`. The v2 save uses `eveniunt-command-center-v2.json` in the app folder. The updated app has no writer for the old path, including its v1 fallback.
Fetch metadata and content for the same authenticated drive and item. Use a version-specific read, or bracket the body read by metadata reads with the same item ID and exact opaque `eTag`. Reject mismatches, missing tags and incomplete bodies.
A missing item is distinct from invalid JSON, an unsupported future version, access refusal and a failed download. A future version gets a reload notice. Only a proven name lookup miss can enter creation.
Reject a renamed or moved item, or a name now bound to a different item. The version-rising build must verify the provider also invalidates the item precondition on a rename/move that could redirect a pending replacement. Use a provider route documented to fail if the name exists *at final creation*. A candidate is a Graph upload session naming the item with conflict behavior `fail`. The build must prove the chosen route and its exact final request.
Keep create disabled until the documentation and ten refused creates against an existing file on personal OneDrive, with byte comparisons, are recorded. Test simultaneous finalization and disabled behavior. The version-rising release waits for that evidence.
Replace by item ID with the exact strong provider precondition (`If-Match` with the observed tag). Never retry by path or with a missing or wildcard tag. Conflict, missing item or changed account starts a fresh read and preview.
After every write require the expected item ID, the new tag and a stable read-back of the exact expected envelope identity/content. An ambiguous reply advances nothing. Rediscover by name and verify the intended item before accepting a later observation.
After a create collision, inspect and merge the winner. When the file vanished, create only under the verified condition. Preserve local proposals and start a fresh file generation. The old cloud file is never a repair source.
The file generation changes on create and damaged-copy overwrite. A generation or item change breaks the local link regardless of counters. Within a generation require retained point and dependency evidence under S13. A counter alone establishes nothing.

**S9. Elect the first legacy reader and finish outages visibly.** [Rejected option: treating unused as spent or sending a legacy read after an ambiguous reply.]
The helper's existing device-handle and allowed-origin checks apply to `POST /legacy-read/claim` with `{device,phase,generation}` and phase `reserve/consume/seal`. Consume also supplies the verified provider item ID and tag. Resolve the authenticated drive using the refreshed Microsoft token, never a caller-supplied identity. Browser and helper use `GET /v1.0/me/drive/special/approot?$select=id,parentReference`, require the folder and drive ID, and for the personal migration accept 1–16 ASCII hex characters, lowercase and left-pad to 16. Hash UTF-8 `bourse-legacy-read/personal-drive/v1`, a zero byte and that value with SHA-256. Unsupported formats and missing identity fail closed for claims. Gate on verified live stability/uniqueness under existing permission. [Helper source](https://github.com/SplitzHappen/Eveniunt-Command-Center/blob/8582f59ed953e43eff29d014177eab2b8e99f63d/tracker/helper/worker.js#L27-L83) · [Existing binding](https://github.com/SplitzHappen/Eveniunt-Command-Center/blob/8582f59ed953e43eff29d014177eab2b8e99f63d/tracker/helper/wrangler.toml#L12-L15) · [Microsoft app-folder API](https://learn.microsoft.com/en-us/graph/onedrive-sharepoint-appfolder).

Ship `tracker/helper/migrations/0001_legacy_read_claims.sql`. Keep one row per drive in D1. State 0 is a renewable election reservation with a **120-second** lease, state 1 is read permission spent, and state 2 is file/manual recovery sealed. Terminal rows never expire or change. Bind the identity and generation as text and require canonical lowercase hex in request validation. The type checks prevent separate text and blob rows for one drive. Check both text and byte lengths so SQLite cannot hide a trailing zero byte from text functions.

```sql
CREATE TABLE legacy_read_claims (
    drive_key TEXT NOT NULL PRIMARY KEY
        CHECK (typeof(drive_key) = 'text' AND length(drive_key) = 64
               AND length(CAST(drive_key AS BLOB)) = 64
               AND drive_key NOT GLOB '*[^0-9a-f]*'),
    generation TEXT NOT NULL
        CHECK (typeof(generation) = 'text' AND length(generation) = 32
               AND length(CAST(generation AS BLOB)) = 32
               AND generation NOT GLOB '*[^0-9a-f]*'),
    state INTEGER NOT NULL DEFAULT 0 CHECK (state IN (0, 1, 2)),
    expires INTEGER NOT NULL CHECK (typeof(expires) = 'integer' AND expires >= 0)
) WITHOUT ROWID;
```

```sql
INSERT INTO legacy_read_claims (drive_key, generation, expires)
VALUES (?1, ?2, unixepoch() + 120)
ON CONFLICT (drive_key) DO UPDATE
SET generation = excluded.generation, expires = excluded.expires
WHERE legacy_read_claims.state = 0 AND legacy_read_claims.expires <= unixepoch()
  AND legacy_read_claims.generation <> excluded.generation;
SELECT generation, state, expires, unixepoch() AS server_now
FROM legacy_read_claims WHERE drive_key = ?1;
UPDATE legacy_read_claims SET state = 1
WHERE drive_key = ?1 AND generation = ?2 AND state = 0;
INSERT INTO legacy_read_claims (drive_key, generation, state, expires)
VALUES (?1, ?2, 2, 0)
ON CONFLICT (drive_key) DO UPDATE SET state = 2, expires = 0
WHERE legacy_read_claims.state = 0 AND legacy_read_claims.expires <= unixepoch();
```

**Reserve, wait, take over.** On a verified v2 name miss and verified create-only capability, persist the attempt generation and local account/epoch. Reserve uses statement 1 and statement 2 together on the primary. Matching live generation returns `reserved` even if the previous response was lost. A live other reservation returns `held` and remaining seconds derived on the server, not `spent`. Poll only while the sync screen is open, with a 120-second ceiling for one wait. Say “Another device is preparing your older save.” A holder may not issue create after its lease expires. A waiter cannot create while held. After expiry, check the name again and, only if still absent, atomically reserve with a fresh generation. An expired epoch or lost local state can no longer act as the holder. Unknown reserve results authorize no operation. A terminal row returns `spent` or `sealed` and permits create-only recovery from local data without a read.
**Create, then consume.** Only the reserved generation whose create is confirmed and read back as that exact pending file may attempt statement 3. Just before consume, check current item/epoch/identity and the unused mode of the file. The helper verifies that the authenticated app-folder path currently resolves to the supplied item and tag. The browser checks the pending generation in the body. The helper checks the reservation generation in D1 and never downloads save contents. If a lease expired during a create already in flight, **only** the generation that actually won and still owns the reserve row can consume. If a different reservation already replaced it, the stale creator cannot read and the new holder must stop when it sees the mismatching file. Recover the visible pending file manually after closing the reservation. A success reporting exactly one changed row grants one old-file request. Recheck the captured account, item, generation and local epoch after the response and before dispatch or staging. Spend the response in memory and send once including the normal provider redirect. No network retry of the legacy request. Losing the consume reply or the staged data can forfeit this automatic read. An already staged body can be reused locally.
**Pending file.** While the exact file has `seed=pending`, allow only matched creator finalization or checked manual closure. All devices, including the creator, hold ordinary content, acknowledgement and log-only writes until the seed is terminal. It may read and show “Another device is preparing your older save”; it keeps its own changes locally. Lease expiry alone does not open writes. Wait for a terminal seed and then restart against the current file. With no progress after 120 seconds from this browser’s first stable pending observation, stop polling and offer explicit “Continue without automatic import”. This recovery may change only the pending seed to `manual`, by current item/tag after verifying the same generation, preserving all file contents. It first needs the terminal D1 decision below or the verified disabled-helper path. An unexpired reservation cannot be sealed. A consumed row cannot issue another read. An in-flight creator whose item/tag or pending seed changed cannot publish a late result. Already downloaded bytes remain local for an explicit file comparison. Neither a timeout nor a lost create reply authorizes a second automatic reader.

**Unavailable, unsupported or abandoned.** Ready v2 files sync without D1. A timeout, missing identity, missing binding, uncertain reply or rewound store holds first create during automatic migration mode. While the sync panel is open retry status at 10 and 30 seconds, then show `Retry cloud sync` and the local backup path. When healthy, resume election or let the player explicitly continue without import. Statement 4 seals a new or expired unused reservation. Verify a terminal primary row before creating a manual file or applying pending-file recovery. A live holder means wait.
If an authenticated provider response supplies a stable nonempty drive identity that is **deterministically outside** the supported migration format, the helper returns `unsupported` before touching D1. Require the browser to verify the same opaque drive identity and genuine v2 name miss. With explicit player approval it can create the v2 file as `seed=manual` through the verified create-only route. It performs zero legacy reads, and other devices use ordinary v2 sync with that provider identity. Missing, inconsistent or transient identity is unavailable, not unsupported. Verify the stable unsupported classification and eligible-format rules before enabling this exception. The fixed migration cannot later admit that drive to automatic reads merely by changing the format or key scheme.
For an untrustworthy claim store, only verified permanent shutdown at the helper, including already open versions, permits first manual create without a terminal row. Disable issuance before an administrative restore. A silent rollback can look valid. Never re-enable automatic claims against an empty or rewound store.

Stage a successful legacy reply as an independent, scoped source and ask about differences. There is no trusted v1 merge base and no bulk “take cloud” on a used device. Check the latest v2 state before applying. Mark the pending copy `imported` after durable staging, `none` if the old file is absent, or `manual` on accepted file/manual recovery. Terminal markers cannot reopen. Other devices bring their local save. Settings can compare a player-supplied older export. Updated software never writes the old file.

**S10. Separate local durability from a cloud acknowledgement.** [Rejected: a mutable sync base in page memory and updating it before the merged data lands.]
At sync start flush the initiating page's intended edits, read the guarded store, then capture its epoch, revision, active edition, tips, drive binding and a fresh attempt ID. Settings uses the full stored document even with zero characters.
Before making a request that can change OneDrive, durably record the expected item/tag (or create-only name), candidate identity and attempt. Allocate the new revision before committing the preparation. Store that post-preparation revision in the attempt and return it to the caller. A preview still binds its relevant values and dependencies under S3. The upload attempt separately binds its post-staging revision. Re-read guard and tokens immediately before dispatch. Restore, replacement, or a changed account cancels a prepared attempt before it is sent. Serialize this last check and dispatch with local replacement.
One implementation is a short transaction covering the main store. Within it, compare tokens and synchronously initiate the prepared fetch within the final read callback. Stage and hash the body before that callback. Never hold an IndexedDB transaction awaiting network I/O.
After stable read-back, recheck account, attempt, epoch and guard. Commit the verified cloud observation and, if the exact verified active edition is durably installed, its installed-point receipt with that active edition. ### Change-log budget

**Trimming removes old explanations of edits. It never removes what a player has saved.** Characters, ticks, lists, stock, active and cancelled receipts, inactive characters’ recoverable records and every module’s saved values survive. Open alternatives and unsent edits survive as actual values with their originating device or cloud proposal. A trim neither accepts a proposal nor cancels a receipt.

Use at most **1 MiB (1,048,576 bytes)** for the serialized cloud log payload, including the encoded proof and replay data. On disk, measure its independently deflated base64 string plus the surrounding log field framing, even for a metadata-only write. Reserve at most **16 KiB** for the separately serialized registry and position headers (64 devices maximum). The provider body cap stays **4,128,768 bytes**. Always encode and measure the whole candidate. If necessary shrink the log below its budget, down to an empty suffix, to fit the protected snapshot and proposals first. An oversize protected snapshot alone is a separate provider-size condition with local save/export intact. A log cannot permanently stop sync.

The planning estimate is about **250 encoded bytes per small edit**, including its graph IDs, operation and share of a position segment. A full 1 MiB is about 4,200 such retained edits, or about **42 days at 100 edits daily** for a heavy player. Deletions, typed stock, large imports and unusually frequent point headers can shorten that window. Dropping already acknowledged entries reduces used space. This estimate is not a retention promise. Measure actual bytes in T34.

**Positions and device acknowledgements.** Within a file generation, count accepted cloud content commits monotonically. The point is `{n,edition,stateHash}`, where `stateHash` binds the canonical protected materialization and the accepted edit frontier. One content commit appends one indivisible point segment. Ack-only writes and trim-only writes change the provider tag, but do not advance the point. The retained floor is itself a point. Every segment binds its exact predecessor point and canonical proof digest. Devices on the same browser storage share a random 128-bit device ID. Sign-in handles, display names, wall-clock times and imported IDs do not establish acknowledgement.

A device acknowledges exactly the verified point durably installed by the S10 finalizer, including its own content upload after stable read-back and guarded installation. Keep the old acknowledgement while unresolved or queued work still needs older proof. A network receipt alone, a read, a declined review or a proposal backup cannot advance it. Issue the ack by a separate conditional write, retrying read/verify, never reusing a tag. The registry uses `deviceId → {ack,order}`. New devices register only after activation of the compared state. Advance `order` by monotone registry update order on genuine advancement or registration. At 64 IDs or 16 KiB, evict the least-recently advanced entry, ties by ID, before registering. Apply the same order until both registry bounds fit. Displacement, reinstall and omitted registry entries mean unknown. Concurrent updates preserve acknowledged points and cannot lower an ack. If the point has passed below the floor before the ack lands, leave the registry unchanged and run the returning-device rule. Never substitute a newer point that was not locally installed.

**Dropping entries.** First drop through the minimum verified acknowledgement among registered entries at or above the current floor, inclusive of proof for reaching it. Entries already below the floor are kept in the registry but excluded from that minimum until they advance to a retained point. With no eligible entries skip acknowledgement-based dropping. Preserve the floor's materialization and any needed newer replay evidence. Then, only when either byte cap still requires it, advance the floor by the oldest complete points until both caps fit. A stale registry entry is only a pruning input. It cannot make a device behind or prove that it is current. Future changes and acks proceed. An offline device cannot pin the log over budget. With no eligible ack, a cap cut can still advance. Empty-suffix fallback checkpoints the accepted head, leaving unsubmitted and unresolved work intact. Never split a point, reassign a device position, or remove a receipt, inactive record or proposal to fit history. With no true content change, trim preserves the accepted point, its state hash, and all protected values.

**Cut representation and verification.** Materialize the accepted floor and retain only the suffix's required proof. An eligible cut keeps all later point segments and their reachable nodes, typed deletions, absorbed operations and equality links. A checkpoint can replace earlier parent bodies by its exact floor frontier. It must reconstruct every surviving point and dependency without older bodies. If a partial cut cannot replay every later point, use a newer complete checkpoint, up to the head. Preserve only the exact restriction of the old proof to surviving points. Keep stock frontier anchors as defined below. Coverage and deletion/absorption indices are scoped to segments, never cumulative lists. Where earlier proposals still depend on trimmed proof, retain their complete checked affected values and identity as detached proposals. Keep each device’s original unsent branch until explicit resolution. A detached cloud proposal preserves all its values if that device never returns. No reapplication is inferred from a detached proposal.

Validate on publication by replaying the surviving interval, checking its exact materializations and stock provenance against the pre-cut graph. Publish with S8's condition. For a combined write+trim, first validate the content transition and then trim its proof. New readers require a nondecreasing floor, valid floor snapshot, contiguous verified predecessor chain to the accepted head, and every previously known **overlapping** point/segment (including deletions and absorbed IDs) with identical proof digests. Recompute digests and check the latest protected projection. Losing still-retained proof, changing a known point, a floor beyond the head, or dropping a protected proposal without a bound approved decision invalidates automatic adoption. With overlap, prove disposition in retained history. With no overlap, retain the local original as a detached proposal and compare. A damaged/foreign copy cannot acknowledge or install automatically. Retain the local original until reconciliation. This permits authorized prefix pruning and still rejects missing retained records.

**Stock through a cut.** In the floor frontier keep, per owner/item/quality, the current own amount and compact provenance for the latest absolute reset: reset ID/type, entered total, own part at that reset, and digest of the exact receipt states it observed. A seed is explicitly a seed. Preserve IDs, amounts and atomic command grouping for relative changes after that reset still needed within the retained comparison horizon. Fold older relative sums at the floor, keeping reset identity and totals. The current frontier holds one provenance anchor per live value or stock group, not an accumulating history. Keep every active/cancelled receipt body and its current state. The retained interval provides actual writer/receipt evidence. The digest alone never proves that a specific unseen change was included. A materialized 51 does not imply “relative only”. Compare typed/relative and receipt evidence over the proved base first, then apply S6. **When stock proof has expired.** If local stock work exists or its absence cannot be proved, compare the full owner/item group and every differing receipt. Proven untouched groups use the returning-device rule below. Show uncertain alternatives as “included in the entered count” or “separate from the entered count”, with the resulting visible amount and receipt state. An approved resolution can set the own part independently of choosing a complete copy. If cloud own stock is 51 after a typed 50 and +1, and the returning device recorded a separate 40-credit purchase, offer 51 with active receipt and own 11, or 91 with that same active receipt and own 51. For a provable unseen −3 against cloud 51, offer 51 if included or 48 if separate, with linked effects intact. For a concurrent Undo of a 40 credit against cloud 56 and own 16, show 56 with the receipt active or 16 with it cancelled. Treat these as proposals, never certain totals. If the underlying action or inclusion is unknown, show whole valid alternatives and require an explicit checked amount/state. Never change a receipt merely because a count or one copy was chosen. Dropping a live receipt requires its own named, approved cancellation, keeping its identity/body. Apply all choices as one validated group under S3/S6.

**Returning device.** “Behind” has one definition: the device's own verified installed receipt for this account, item and generation has a point strictly earlier than the current validated floor. The registry acknowledgement may lag without changing that classification. A device with no usable receipt or registration is separately unknown. A device at the floor is within the log when its exact point validates. A retained, verified point for a registered device permits ordinary related reconciliation. An unknown, replaced or behind device gets a labelled comparison. Keep “Deleted elsewhere” for exact retained tombstones and “Only on this device — it may have been deleted elsewhere” where proof is gone, with symmetric wording for uncertain cloud-only values.

**Plain rule for a device with no local edits.** If the device can prove it kept the last copy it actually synced, gather the newer cloud changes into a single review. The player can accept them together and receives the usual confirmation for anything that would be removed. The device sends back no old items. Lists, stock, receipts, levels and ticks follow the same rule.

For that shortcut require the guarded installed receipt, same verified account/item/generation, a valid current cloud head, and complete local proof of no writes since that exact point on the affected dependency group. Require the receipt’s epoch, or S12’s explicit continuity for an untouched scope. Reuse the locally retained installed-point root and the local ancestry/intent record. Regard even a reverted write, queued work, pending proposal or replacement touching the closure as local work. Byte equality of displayed values cannot prove no writes. Missing evidence is uncertain. Stage cloud-only additions and edits for one labelled “Accept cloud changes” action. Show uncovered deletions and other losses together for normal receiving confirmation before applying them. A decline preserves the affected groups, with no ack for the uninstalled point. Apply compatible changes atomically, keep independent local work, and recheck the preview at commit. Prompt individually only for changed or unproved local groups and their coupled effects. No bulk Keep/Take for uncertain values and no upload from the comparison alone. After a guarded resolution at the current point register or advance the ack.

**Local storage and collection.**
- In the existing IndexedDB store use `main`, `main-rev`, `main-guard` and `main-guard-rev`. Commit independent snapshot roots and guard pages, one shared set of immutable `node:<id>` rows, 128-bit epoch/revision tokens, and device metadata atomically. Pages are content-addressed path-copy nodes of a fixed-fanout typed-key map (fanout 16, ordinary leaves ≤16 KiB). Stage large work in bounded transactions before publishing its roots. An indexed preparation token names the immutable inputs and expected revision.
- Reserve internal key prefixes away from rescue extras. The reachability roots are main, guard, acknowledged receipts, pending tips/queued intents, archive references and live stage/attempt manifests. An archive may be an immutable compressed blob, without pinning snapshot pages. Tag each queued command with original ID and epoch. `device.tracker.sync` retains `fc,backupAt,drive`; verified `drive={account,item,tag,generation,bodyHash,observed,proofRef,installed?,at}`. `observed` is the latest verified cloud point. `installed={point,root,epoch}` names the guarded local materialization of the last fully installed point for the same account/item/generation. Pin this root and the local write evidence needed to classify its groups until the next installed point. Clear or scope-fence it on replacement under S12. Neither a cloud observation nor a registry acknowledgement substitutes for it. `device.transport.attempt` records ID, epoch, revision, account, item/tag or create target, and body digest. `legacyStage` names staged bytes and status. Provider strings ≤2,048 bytes. Purchase done IDs live at least 24 hours and through their retry. Guards recover main/pointers, not loss of immutable nodes needed by both.
- Queue collection work after every committed root change; coalesce passes. In a worker trace roots from one recorded root revision, and collect unreachable obsolete pages, unreferenced staging and nodes only. Delete in transactions of at most 128 records/1 MiB of ordinary data (one larger wholly unreachable record may be deleted alone). Check the root revision and stage tokens in each transaction and abandon stale marks. All root/stage publications and removals change that revision. Publication rechecks the existence of referenced rows in the same transaction, so a stage reclaimed before publication must be rebuilt. A reader encountering missing data from an obsolete captured root retries from current roots; missing live data enters recovery. Staged data with no current live reference may be reclaimed; a still-pending command keeps its intent and can reprepare. Never reclaim live deletion witnesses or unsubmitted branches.
- Try a bounded reclamation pass before clearing prices after a quota failure. Keep writing only if the guarded operation fits. Under continuous churn, interleave collection batches between commit attempts, rather than wait for another cut. The steady-state ordinary-edit allowance is the live page footprint plus at most 8 MiB of unreachable snapshot pages after quiescent collection. Report pending/archived/history bytes separately. An interrupted collection is restartable; unreachable garbage is never treated as current data.

**Decode limits.** Total expanded cloud/transfer content is at most 64 MiB per file. Transfer text is at most 4 MiB. Cloud wire cap is in S13. Count during bounded streaming decode in a worker (duplicate-key rejection, depth ≤128, iterative validation, cancellation). Keep native active backup decode at 64 MiB and offer larger raw recovery bytes as streams. Preserve bytes if checking fails before cleanup/normalization. The existing cleaner slices data and must never silently validate by deleting it. Existing oversized data stays exportable. `tracker/src/core/cloud.js:142,163–170` · `tracker/src/core/codec.js:98,121–134` · `tracker/src/core/save.js:30–38,192–199`.
Editor limits remain 200 watches, 500 own items and 2,000 purchases for the current trip. Valid imported data above these caps remains readable, editable and undoable. Refuse only new excess entries. Decode or size refusal leaves the previous saved edition intact.
