# Bourse · Save and sync

Owner-requested revision and full replacement of the Bourse save-and-sync design. Authored with Codex, OpenAI GPT-6 family (`gpt-6.2-sol`).
Public design and source baseline `5092105c11fb10e9853fbf6afcbb1ed3603bae79`.

## 1. How a device knows what happened

A save records each edit and what the player had seen when making it. A removal leaves a record, so an old copy cannot bring back the item by itself.
When two used devices link, shared values become one starting point. A later edit made on either device still counts, even if that device missed the link.
A new character in a reused slot gets its own identity. The previous character's work stays with that character.
Each purchase counts once. If a typed figure might already include a purchase recorded elsewhere, the player sees the possible totals before choosing.
A short recent history keeps routine sync small. A device older than that history compares its saved copy before any difference is applied.
Cloud writes can replace only the copy they read. An older browser can keep working locally and carry its save by file.

## 2. Decisions

**S1. Save editions and edits.** [Rejected option: infer what happened from two snapshots or their timestamps.]
The readable shared fields are the materialization of one accepted edition. Recent transactions form a directed acyclic graph. A node records its parents and its exact logical writes. A parent is an edition the player or a validated reconciliation actually applied.
A removal is a typed tombstone. Missing legacy scope, absent field, present zero and removal are different states. A reset to a previous value is a new write.
Make one node per committed debounce burst or checked user command, including all the fields of a compound action. A node contains deltas. Idle sync, unchanged reads and repeated delivery create no node. Hold distinct tips until a join or decision dominates them. S13 cuts only a proved stable prefix.

**S2. Join histories at the path they share.** [Rejected option: use the most recent upload, choose an arbitrary common ancestor, or treat a link as a new edit of every field.]
Union validated nodes by identity and derive the maximal writers of each path. For each pair of writes to a path, discard the older one only if the newer one provably supersedes it. Equal surviving values may be displayed together. Unequal surviving values require a decision unless a rule in S4 or S6 specifies a compatible join.
Distinct seed histories need a reviewed bridge. Materialize one fully covered outcome over all represented paths: explicitly decide unequal values, including unequal absences, and explicitly adopt the origin writes for every equal value and equal recorded tombstone. Paths represented by only one source keep that source's writes. Mere absence in a source that never represented a path has no effect.
For an equal path the bridge records an **equivalence**, consisting of the exact maximal same-value write IDs in its parents. It represents those writes as one logical predecessor, with no extra competing writer. A later edit descended from any member supersedes the matched predecessor, even if its author never saw the bridge. The same applies to a deletion. A later write that changes a bridged value expressly supersedes the matched class. A bridge's actual decision between unequal writes is an ordinary write with the bridge's parents and does compete with a concurrent edit.
For a path, first respect actual causal edges. Contract only the validated same-path equivalences in the relevant ancestry. Use the transitive closure of strict supersession between the resulting classes. A new equivalence may join only incomparable, byte-equal maximal representatives in its own parent view. If independently made bridges create a cycle after contraction, **skip equivalence reduction for that path's conflict group** and offer the surviving values from the original causal graph. Keep the raw evidence. An explicit resolution over all covered originals becomes an ordinary write and hides those disputed aliases wherever that resolution dominates. Never pick a “winner” from the cycle.
Example: A and B start with tick X. Join their equal writes in M. A removes X while offline, then receives M. Its explicit removal supersedes the shared predecessor. Apply the normal removal confirmation, with no misleading “edited on the other device” choice. A real concurrent value change still requires review.
If the cloud is foreign, a file has rolled back, a device predates a checkpoint, or an import replaced a particular scope, use checked scope comparison for the affected units. Show all unequal values and one-sided entries in that scope. Missing evidence never means removal. A truly unused device may only accept or defer; check all modules, history, pending changes, settings and character detail before offering that shortcut.

**S3. Keep valid editions while asking.** [Rejected option: an all-tips preview token, provisional stock totals, and a mutable per-key base.]
Each device and the cloud have a valid active edition and outstanding tips. Persist competing tips before showing them. A conditional cloud write can carry proposals without changing the cloud's active edition. Show local-only while transmission is unconfirmed. A third device's proposal is retained even if it has never seen the question.
A preview token binds just the conflict group: canonical affected paths, exact maximal writer IDs and values, proposed effects, and the closure of dependencies plus their observed writers, including expected absence. Dependencies include slot occupancy, children, list selection, stock receipts and any touched constraints. In a detached group bind the immutable source identity and its affected scope slice. Hash only that slice, including scoped absences, so an unrelated edit to the live document cannot invalidate the answer. Use the local epoch, account and cloud generation as context.
At commit re-read the actual current local and cloud snapshots. Recompute the group and its dependencies. If any shown input, membership or effect changed, refresh that group before accepting the answer. Unrelated local or remote edits can rebase the accepted group onto the latest heads silently. Provider preconditions still use the **current** item and tag. A failed conditional write repeats the read and dependency check before sending. Keep accepted answers in the current preview until all groups required for one valid join are answered. Unrelated edits remain durable as separate tips. The join consumes a resolved preview only after each answer still matches.
If independent answers are submitted in one transaction, each is revalidated. Unanswered groups keep their alternatives and each device's last valid edition for those groups. Independent validated edits may continue and be backed up. If a partial active edition would split a dependency group or claim a merge parent it has not applied, publish proposals only. Store no provisional count and no sync acknowledgement for an unconfirmed upload.
Freeze writes that would change a disputed group's inputs or outputs, including craft ingredients, stock outputs, hand-ins and Undo. Rejections roll back the whole command. A decision writes the chosen values or tombstones and the exact alternatives it settles. Conflicting decisions remain separate edits. Settings may offer “Answer now” during automatic sync and open the preview after sign-in or a manual request. Tracker waits until visible.

**S4. Preserve identities, dependencies and consent.** [Rejected option: treating slot names as permanent identities, borrowing one base for all module rules, or use of the clock to decide which new record wins.]
Keep the public slot labels `c1` through `c8`. Every actual character creation receives a random immutable incarnation. Slot occupancy names that incarnation. Profile fields, Tracker ticks, exclusions, levels, and all other slot-bound values and links refer to an incarnation in history. Index them by slot only when materializing the compatibility fields.
Removing a character records a removal of its incarnation and shows the dependent work being removed or retained. A later change made offline to that incarnation's descendants, even a brand-new tick, conflicts with the removal. A new incarnation in the same slot is an independent character. Never apply old descendants or the placeholder-name shortcut to it. A placeholder can yield only inside a proved existing identity.
The preview may retain the new character, restore the old one, or keep both if a free slot is shown and the player approves the move. Retain unassigned character-linked data with its original identity in the saved document. A slot-bound Atelier profile or stock group becomes archived for that incarnation, Lists and company links become unassigned with their old association recoverable, and voyages, purchases and crafts keep their records. Never transfer such data to a reused slot without explicit reassignment. Zero active characters is valid. No adapter creates one from orphan ticks. Fenced refresh/bookkeeping likewise never writes into a reused slot.
During first import of legacy character slots, assign new incarnations. Across independent seeds do not equate same-number slots automatically. Compare shown identities and child data. A player-approved “same character” mapping aligns those incarnation paths through S2's bridge, leaves old labels in history and routes late writes through the mapping. Incompatible independent mappings reopen the identity question. A legacy module-only import resolves old links against one shown mapping or keeps them unassigned.
Keep an existing subrecord's character identity separate from the slot change. Evaluate Lists and Submersibles integrity as dependency groups after assembling candidates. Show children, fleets and voyages affected by removal. Retain the existing cap/slot/child constraints and safe discovery union.
Use a base only for a rule that requires one. For the affected path or field, find all maximal common ancestors of the candidate tips. Resolve each ancestor's value with the same validated reducer. If all agree, use that value. If they are ambiguous or differ, there is no proved base for that field. Use only order-independent compatible rules such as discovery union, or ask. For Submersibles, merge name/world/owner by field with that rule and ask about divergent ambiguous fields. Apply the existing max-slots/min-order treatment to concurrent compatible field edits. A company removal or new slot collision uses the whole dependency group.
For a List or target created twice under one ID, use the native creation node (or reviewed source identity), not `made` or `at`, to distinguish origins. If distinct and provable, keep both, sorted by full creation digest. The smaller digest keeps the old ID. Derive a free, valid 16-character lower-case base-36 ID for the other from a domain-labelled hash of record type, original ID, creation digest and increasing salt. Test in ascending salt order against occupied IDs and the other allocations. Store the allocation as an ordinary join write and refer to each record by its creation identity in history, so late edits follow its assigned label. Carry children, step links, selection and purchase source associations. If birth or ownership is ambiguous, show both complete groups and wait. Never overwrite just because times are equal.
Before changing an active edition, compare the proposed effects with every participating active input. Applying a tombstone or discarding a live alternative requires explicit consent covering that exact write and dependent changes. An old consent never authorizes an unseen addition or edit. Keep Tracker's incoming-tick removal confirmation. Local erase, restore and import grant no authority to delete a remote value. A stock action may authorize precisely what its confirmation states.

**S5. Prepare deltas before the guarded local write.** [Rejected option: process the full graph in IndexedDB's synchronous callback or write two copies of it.]
A page supplies intended changes, before-values, epoch and current edition. Read saved main, guard and checked indices. On a worker prepare the logical delta, resulting projection, staged snapshot records, and digests outside the write transaction. Verify incoming nodes once. Use maintained path, node and dependency indices for ordinary edits. Build/revalidate those indices off-thread if missing. Never trust an index to replace its verified records.
Open a short IndexedDB write transaction only after preparation. Read the row tokens, main and guard records and expected snapshot identities in that transaction. Compare the epoch, expected revision and all read/write tokens. If a revision changed, abort cleanly and reprepare from the actual saved edition while keeping the original intent. Disjoint edits can retry. A changed dependency or mismatched epoch makes the draft a visible refusal. Limit automatic contention retries to two.
Store immutable nodes once per ID in separate keys within the same object store as main. Store new content-addressed snapshot pages and independent guarded snapshot pages for touched modules only. A path-copied map of fixed-fanout pages keeps a one-row edit from cloning a large section. Changes commit page roots, main/current tips, guard, revision and device metadata together. The complete historical graph is neither replayed nor copied at commit. See §3 for storage layout and recovery.
Keep `main` readable as a v2 envelope for the older writer boundary. Older compiled pages must still reject it before touching shared data. Old `main` stays reachable until migration has committed. Success callbacks receive the committed projection. Both notification channels may refresh displays. Correctness is independent of delivery.
Only the guarded sync finalizer writes a non-null cloud receipt. Replacements rotate the local epoch and invalidate an in-flight attempt. Preserve the cloud identity witness when the selected bytes still justify it. S12's scoped replacement operation decides which paths must be reviewed. Only the owning successful operation updates each `fc` or `backupAt` field.

**S6. Keep stock and purchase evidence together.** [Rejected option: merge displayed totals, clamp a joined sum, or assume a typed answer excluded an unseen receipt.]
Each Lists owner, incarnation and item has its own-stock amounts and immutable purchase bodies with active or cancelled state. The projection for each quality is own stock plus its active credits. Collectables have no Bourse credits. A missing displayed value reads as zero and can coexist with receipts. Own stock can be negative. A materialization must lie in 0–999,999 in every quality.
At every v2 seed encode own-stock paths, including groups with no receipts. Preserve the precise legacy representation on untouched groups. Without any credit history keep applicable Lists merge restrictions and guards. A Bourse tick or Undo changes a receipt, leaving own stock alone. An ordinary Lists stock command computes its already-checked visible result, then subtracts the active credits it actually saw. For each affected quality record the displayed result and a digest of the observed receipt frontier. Compute it from sorted receipt IDs with exact state-writer IDs, including cancellations, in the checked parent view.
For two related branches, resolve own amounts and individual receipt states by their causal histories, then check the whole group. If an actual own-part change and any credit addition, cancellation or reactivation for the same stock group are concurrent, ask even when there is only one own writer. Portably keep each active edition intact. Disjoint owner/item groups operate independently. A sequential own edit that saw the receipt state incorporates it once.
From 10, one device buys 40 and another types 50. Show “50 with the purchase included” (own part 10), and “90 if the 50 was separate” (own part 50), naming the receipt and both meanings. Offer the existing branch outcomes and any explicit valid combination with a chosen count or receipt state. For a cancellation show the corresponding valid totals and whether the purchase remains counted. Keep paired changes atomic, including every other touched quality, craft action, or target. A checked answer preserves cancelled receipt identities.
Two different purchases of 40 from 10 still produce 90: neither changed own stock. One receipt ID counts once. An explained Undo supersedes its actual receipt state. A missing receipt with no proved action never counts as Undo. Reject conflicting immutable bodies, invalid counts and corrupt projections before offering choices. A choice that rejects a receipt records its cancellation with the body. Reactivating it later needs an explicit checked decision that saw the cancellation.

**S7. Bind a tick to what the player bought.** [Rejected: inferring a purchase from a change in demand or crediting each selected list for the entire row.]
Default to “Tick only”. With “Also add to I have in Lists”, allocate the purchased amount across the displayed owners using the plan's stable share order. Verify the selected lists, quantities, per-owner source targets, trip and existing marks inside the write.
Record each owner's actual purchase and actual credit. Own trip items always credit zero. At the cap, show the purchased and accepted quantities separately. From 999,990 a purchase of 40 records 40 bought, 9 credited, and 31 uncredited. If any Lists part refuses, commit none and offer a separate tick-only action.
For a combined row allocate in the order `c1…c8,u,x`, each limited to its outstanding need. Quantities beyond the outstanding need require the player to edit the purchase before recording it. Generate the purchase IDs once before dispatch. Retry only that command in its original page for at most two minutes and three attempts. Read the receipt, tombstone or local completion record before retrying. An unknown result after expiry requires a fresh view.
A purchase stays bound to the exact wanted items and amounts behind the displayed need. Subtract the uncredited part once. A different source, unexpected need, or incompatible check mark displays “To check” and excludes the row from a spending total.
For an own item, the remaining quantity is its trip quantity less the sum of active purchases, floored at zero. For a Lists row, consider only this trip, owner, item and quality. Use the causally latest active purchase/check anchors. All simultaneous latest anchors must agree on the source fingerprint and expected need after their own credit (`of − cr`). If that equals the actual current need, subtract the sum of active uncredited units (`n − cr`) once, with a floor of zero. Otherwise keep the marks and show “To check”. No display count participates in a stock write.
“Still count” writes a check against the current sources. Removing an uncredited mark requires confirmation. Undo of a credited purchase verifies the whole action and current stock, subtracts the recorded credit only if enough remains, and records the cancellation.
Allocate a trip on the first add, tick or shopping-list copy in the same write. “New trip” creates a fresh ID, clears only this trip's own items and uncredited marks after confirmation, and keeps previous credits and their Undo available.
Two offline starts get different IDs. Ask which trip to display. Keep the other trip and its own quantities accessible. A change of selection or current trip never cancels a receipt.
Hide the credit switch automatically when its build tests fail. Retain the reader and indivisible stock-group guard in the off build. With existing credit history, display/export it and refuse stock-changing actions or divergent merges for that group with an explanation.
Tick-only still works for unblocked rows. Never apply a cached `lists` preference as a grant of credit in the off build. A credit-enabled build can finish a held decision.

**S8. Use a separate cloud file and conditional writes.** [Rejected: blind path replacement, a best-effort create followed by a read, or a tag unrelated to the downloaded bytes.]
The legacy file is `eveniunt-command-center.json`. The v2 save uses `eveniunt-command-center-v2.json` in the app folder. The updated app has no writer for the old path, including its v1 fallback.
Fetch metadata and content for the same authenticated drive and item. Use a version-specific read, or bracket the body read by metadata reads with the same item ID and exact opaque `eTag`. Reject mismatches, missing tags and incomplete bodies.
A missing item is distinct from invalid JSON, an unsupported future version, access refusal and a failed download. A future version gets a reload notice. Only a proven name lookup miss can enter creation.
Reject a renamed or moved item, or a name now bound to a different item. The version-rising build must verify the provider also invalidates the item precondition on a rename/move that could redirect a pending replacement. Use a provider route documented to fail if the name exists *at final creation*. A candidate is a Graph upload session naming the item with conflict behavior `fail`. The build must prove the chosen route and its exact final request.
Keep create disabled until the documentation and ten refused creates against an existing file on personal OneDrive, with byte comparisons, are recorded. Test simultaneous finalization and disabled behavior. The version-rising release waits for that evidence.
Replace by item ID with the exact strong provider precondition (`If-Match` with the observed tag). Never retry by path or with a missing or wildcard tag. Conflict, missing item or changed account starts a fresh read and preview.
After every write require the expected item ID, the new tag and a stable read-back of the exact expected envelope identity/content. An ambiguous reply advances nothing. Rediscover by name and verify the intended item before accepting a later observation.
After a create collision, inspect and merge the winner. When the file vanished, create only under the verified condition. Preserve local proposals and start a fresh file generation. The old cloud file is never a repair source.
The file generation changes on create and damaged-copy overwrite. A generation or item change breaks the local link regardless of counters. Within a generation use actual parent containment, never an upload count, to establish ancestry.

**S9. Use the sign-in helper for the single automatic legacy read.** [Rejected option: a device or file flag that disappears when both copies are cleared, or a check-then-write in eventually consistent storage.]
Keep the existing sign-in device store. The helper's token adapter discards Microsoft identity information and stores a refresh token plus timestamps, and the configuration currently declares only the device KV binding. Add one D1 binding, separate from the existing store. [Pinned helper adapter](https://github.com/SplitzHappen/Eveniunt-Command-Center/blob/5092105c11fb10e9853fbf6afcbb1ed3603bae79/tracker/helper/worker.js#L27-L77) · [Pinned bindings](https://github.com/SplitzHappen/Eveniunt-Command-Center/blob/5092105c11fb10e9853fbf6afcbb1ed3603bae79/tracker/helper/wrangler.toml#L12-L15).

**Drive identity and authorization.** Add POST `/legacy-read/claim` using the existing origin allowlist and valid 64-hex device-handle gate. Request fields are `device` and the proposed 32-hex cloud generation. The handler looks up the sign-in and uses the existing refresh flow. Share the refresh-token rotation and sign-out/error behavior with `/token`. Do not accept an identity or sign-in token supplied as a claim parameter. Do not decode or store an ID token.
With the Microsoft access token from that refresh, the helper calls `GET https://graph.microsoft.com/v1.0/me/drive/special/approot?$select=id,parentReference`, accepts a successful DriveItem with nonempty `parentReference.driveId` and a valid folder item ID, and uses a domain-separated SHA-256 of the exact case-sensitive drive ID as `drive_key`. Bound each provider identifier to 2,048 UTF-8 bytes. No guessing from user profile text or fallback to device ID. Missing scope, lost identity or different drive stops the claim. The client obtains the same key using the verified app-folder identity under the token that performs its cloud operation. Before using a grant, compare drive, epoch, generation and current sign-in. The helper never sees save data. The app-folder endpoint and parent reference are documented. Availability of this property on the actual personal account under the existing delegated permission is a build gate. **D1 migration and claim.** The builder ships `tracker/helper/migrations/0001_legacy_read_claims.sql` with the following schema. It is one non-expiring row per account drive. A repaired, deleted or renamed save file never clears it. Its generation field is only diagnostic and binds the winning invocation's returned grant.

```sql
CREATE TABLE legacy_read_claims (
    drive_key TEXT NOT NULL PRIMARY KEY CHECK (length(drive_key) = 64),
    generation TEXT NOT NULL CHECK (length(generation) = 32)
) WITHOUT ROWID;
```

Use one D1 write on the bound database for election. Bind both values as parameters. Execute via `env.LEGACY_READS.prepare(sql).bind(driveKey, generation).run()`. A successful write reporting exactly one change returns `granted` plus the drive key and generation. Zero changes returns `spent`, even for the same generation. An error or missing result returns `unavailable`. A retry never reissues a spent grant. The table is never read and then written as two election steps.

```sql
INSERT INTO legacy_read_claims (drive_key, generation) VALUES (?1, ?2)
ON CONFLICT (drive_key) DO NOTHING;
```

**Normal rollout and failures.** An existing v2 file is read and synced with S8–S10 without consulting D1. A guarded device finding a verified name miss first checks whether creation is enabled and prepares its guarded edition. Before making an initial create, claim the drive's single chance. A loser rereads v2 and can sync the winner. If the file is still absent, a known-spent browser may create from its own save only. A store error or unknown outcome holds initial creation, with local work and files still available. A browser with a prior v2 receipt and a lost v2 file uses create-only recovery from its local save, and never asks to read the legacy file.
Only the live invocation with the grant and an acknowledged create/read-back of the exact pending generation dispatches the automatic legacy read. It consumes the grant from memory before sending one logical request, including the provider's download redirect. No internal retry, background task or later rerun sends another request. Stop if another create won. Any lost claim/create response or crash before durable staging can forfeit the one automatic chance. Once staged, retries read the staged bytes from disk. Existing older applications may still use their original file.
The first legacy body is an independent source. Compare only represented fields and require explicit decisions on each one-sided or unequal group. An older receipt has no authenticated drive binding, so use **no legacy base**. Group and expand previews without a bulk “take cloud” action on a used device. This costs more review on the first link. Resolve against the current v2 item and keep other modules' omitted fields. A confirmed miss marks `seed=none`. Valid content incorporated into a durable proposal marks `imported`. A player who continues without this automatic move can acknowledge `manual`. Never undo a finalized seed marker or re-read on a replacement.
Settings offers “Bring in a saved copy” for an older device that lost local data. The player can select a prior app backup or a file they downloaded themselves from their own older OneDrive app folder. Decode the legacy cloud envelope locally, show scoped differences and use S12. This never fetches or writes the old path. Edits lost from all copies are unrecoverable.
Protect the database like migration state. The product never deletes rows, changes the drive-key scheme, resets D1, or reconstructs a blank table on request. Missing or mistaken bindings fail the claim. If the original database was reset or restored to an earlier point, disable claims until continuity can be proved. If it cannot be proved, permanently disable automatic legacy reads for this deployment and use player-supplied files. The owner must treat any rollback or database replacement as a grant outage before reconnecting the helper. D1 uniqueness cannot detect an administrator silently rewinding the whole database.

**S10. Separate local durability from a cloud acknowledgement.** [Rejected: a mutable sync base in page memory and updating it before the merged data lands.]
At sync start flush the initiating page's intended edits, read the guarded store, then capture its epoch, revision, active edition, tips, drive binding and a fresh attempt ID. Settings uses the full stored document even with zero characters.
Before making a request that can change OneDrive, durably record the expected item/tag (or create-only name), candidate identity and attempt. Allocate the new revision before committing the preparation. Store that post-preparation revision in the attempt and return it to the caller. A preview drawn after a staging write binds to the post-staging revision as well. Re-read guard and tokens immediately before dispatch. Restore, replacement, or a changed account cancels a prepared attempt before it is sent. Serialize this last check and dispatch with local replacement.
One implementation is a short transaction covering the main store. Within it, compare tokens and synchronously initiate the prepared fetch within the final read callback. Stage and hash the body before that callback. Never hold an IndexedDB transaction awaiting network I/O.
On response, recheck the account, attempt, epoch and guard in a fresh write. Install exactly the acknowledged save/receipt together. If only ordinary edits intervened, retain their branch and reconcile from the actual stored edition. The receipt points to exactly the cloud active and tips last witnessed. It never claims that an unadopted cloud edition has been applied locally. Never run a silent default-choice second merge.
A changed epoch or recovery state discards the callback. An in-flight HTTP request may already have arrived. Show an unconfirmed attempt until a fresh stable read establishes its outcome. Its item/tag condition protects intervening cloud writes. Local Restore always works offline.
A lost response, quota failure after upload, partial identity or superseded attempt cannot mark the device synced. On restart read the cloud again before sending. Identical verified content needs no upload. Keep a confirmed backup time separate from a completed reconciliation.
For damaged bytes, first offer download, then ask explicitly to replace the displayed copy with this device's checked edition. Bind consent to exact old bytes/identity, local revision, account and epoch. Refuse unsupported future formats, absent tags and unstable reads.
If another device repaired it, read and merge that sound copy. An exact return of older valid cloud bytes can have the same item and generation. Compare the fresh graph with the last confirmed active edition **and every then-confirmed tip**. Missing prior history breaks the link, even if a counter or one common ancestor matches. An exact body match or proved containment allows normal comparison. A confirmed overwrite starts a new generation with no authority from the damaged file. Retain validated pending local editions. Other devices compare afresh. A normal checkpoint publication uses only the exact closing-tip exception in S13. A damaged-copy overwrite cannot use it.

**S11. Release the erase fix first and keep a local guard.** [Rejected: relying on a cache expiry date, or writing the safety copy in a later request.]
